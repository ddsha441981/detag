## ADR-0018 — PF-5003 `CacheUnavailable`: the Redis failover error (2026-11-12, Phase 0)
**Context:** P0-051 ("failover error mapping to typed errors") found no typed error for Redis failures: `AppError` had only `DatabaseUnavailable` (PF-5001, Postgres) and the redis modules each carried their own `Pool`/`Redis` error variants with no mapping to the API taxonomy. PF-5002 was already taken (`InvalidStateTransition`).
**Decision:** New variant `AppError::CacheUnavailable` — PF-5003, HTTP 503, title `cache_unavailable`, safe detail "the cache is temporarily unavailable". `From` impls map `deadpool_redis::PoolError`, `redis::RedisError`, and the `Pool`/`Redis` variants of `CacheError`/`RateLimitError`/`PubSubError` to it; all other module-error variants map to `Internal` (programmer/caller errors, not failover). **Consequences:** Any Redis outage now surfaces as a typed, PII-free 503. The exhaustive taxonomy tests (34 variants) pin the code. If a future ticket needs to distinguish checkout vs command failures, it must add variants, not match on provider strings.

## ADR-0022 — Argon2id defaults m = 64 MiB, t = 3, p = 4 + rehash-on-login (2026-11-13, Phase 1)
**Context:** P1-027's spec sets the Argon2id defaults to m = 64 MB, t = 3, p = 4 — stronger than the OWASP first choice (m = 19 MiB, t = 2, p = 1) that P1-001 shipped. Every account created before this change carries the old params in its stored PHC hash.
**Decision:** Defaults are m = 65536 KiB, t = 3, p = 4 (`PF_ARGON2_*`, still operator-configurable with the same validated ranges). Old hashes are NOT bulk-rewritten: login upgrades them lazily — on a successful login, when the stored PHC params differ from the current policy, the just-verified password is rehashed with the current params and the new hash is written in the same transaction as the session row (`needs_rehash` in `crates/core/src/password.rs`, wired in `apps/api/src/services/login.rs`). The rehash is opportunistic (a hash failure logs a warn and the login still succeeds) and runs before the transaction so it never holds a pool connection. Measured cost (`cargo bench -p detag-core --bench argon2`, criterion, 10 samples, 2026-11-13 on the 1.5-CPU build VM — an upper bound for the 4-vCPU target VPS): hash ~195 ms and verify ~192 ms at the new defaults, vs ~26 ms / ~29 ms at the old ones. The full note (incl. the 64 MiB-per-hash sizing for login bursts) is in the deploy runbook.
**Consequences:** Every login/register pays ~0.2 s of Argon2id (was ~0.03 s); a pre-P1-027 user pays one extra ~0.2 s hash on their first login after the upgrade. The sync-hash-on-async-worker concern (PERF-001) covers this path too — the rehash follows register's existing inline-hash pattern rather than inventing a new one. If the cost ever needs cutting, the operator lowers `PF_ARGON2_*` in the deployment env; the fleet then converges via rehash-on-login with no migration.

## ADR-0023 — Email send caps enforced at the drain, not at enqueue (2026-11-14, Phase 1)
**Context:** P1-031's spec sets per-recipient hourly caps per template class (verify 3, reset 3, marketing 0) with abuse-log entries on trips. The cap is on SENDS, and mails are enqueued from many services (register, resend, forgot, email-change, lockout, …).
**Decision:** Enforce in the drain (`crates/mailer/src/drain.rs`), the single choke point every queued mail passes through — not at each enqueue site, where a new service would silently dodge the cap. The drain counts sent rows for the recipient's hash + the class's templates in the last hour (`email_outbox::count_sent_recent_for_recipient`; `sent_at` in-window, so queued-but-unsent rows spend nothing) and, on a trip, parks the row (the mail is dropped, not retried into the next hour — its token would be stale by then) and writes an abuse audit row (`email.rate_limit_tripped`, hash + template + class + cap + count, never a raw address, NFR-42). A failed audit insert logs loudly but the row is still parked — enforcement never depends on the log write. A count-query failure is transient (the row is rescheduled, not lost). Caps are operator config (`PF_MAILER_VERIFY_CAP_PER_HOUR` 3 / `PF_MAILER_RESET_CAP_PER_HOUR` 3 / `PF_MAILER_MARKETING_CAP_PER_HOUR` 0). Transactional alerts (`lockout-notice`, `new-login-digest`, …) are never capped — a lockout notice must reach the user precisely when the account is being hammered. Marketing is 0 with no marketing template shipping in v1, so any marketing-class row is parked on sight until the operator deliberately raises the cap.
**Consequences:** The endpoint-level limits stay as the first line (resend 3/hour per user+template, P1-002; forgot 10 burst / 1 per min per account, P1-025); the drain cap is the backstop that catches cross-endpoint combinations (register + resends + an email change adding up to more than 3 verification mails to one address in an hour). A capped mail's caller already got its 204 — the drop is visible only in the audit log and the row's `last_error`, which is the same visibility the lockout-notice path already has.

## ADR-0024 — API keys verify against an `active` owner; suspend does not revoke keys (2026-11-14, Phase 1)
**Context:** P1-034's extractor verifies a `pf_live_*` key by hash lookup and loads the owner. Suspend (`POST /v1/admin/users/{id}/suspend`, P1-008) revokes the user's sessions and blocks the next login — but it touches no `api_keys` row. The JWT path deliberately does NOT check user status in the extractor (P1-008): suspension revokes sessions at suspend time and a pre-suspension access token dies in ≤ 15 min anyway. A key has no expiry, so the same reasoning does not apply — without a status check, a suspended user's key would keep working forever, and the suspension would be bypassable by any key the user minted before it.
**Decision:** The key leg rejects any key whose owner is not `active` — 401 `PF-1001`, indistinguishable from an unknown hash, a revoked key, or a missing owner (the response never says which). The JWT leg is unchanged (still no status check — the ≤ 15 min residual window is P1-008's recorded trade-off). No new revoke-on-suspend behaviour: suspend still does not flip `api_keys` rows — if the owner later wants suspend to revoke keys too, that is a one-line addition to the suspend transaction (revoke keys + audit), and the extractor check stays as the backstop either way. A `deletion_pending` owner likewise cannot use keys (status is not `active`).
**Consequences:** A suspended user's keys stop working at the next request (no residual window, unlike access tokens). Restoring the user (`active` again) restores the keys with no re-mint — the check reads the live row, so there is nothing to undo. Recorded as the P1-034 behaviour in the api-spec extractor paragraph and proven by test (`api_key_of_suspended_user_is_unauthenticated`).

## ADR-0025 — Plan catalog: 5-minute in-memory cache, explicit invalidation; resolution pins trialing/active + newest-wins (2026-11-15, Phase 1)
**Context:** P1-049's spec says "catalog from db (seeded) + cache" without naming the cache or its TTL, and the resolution rule ("subscription override") leaves the edge cases open: which subscription statuses count, what wins when several live subscriptions exist, and what happens when the Free plan is missing. The profile (P1-005) already resolved the plan per request with two DB reads; every later consumer (quota middleware P1-051, `GET /v1/plans`, admin plan editor P1-057) will resolve it too, so the rule needs one home.
**Decision:** The catalog is `detag_core::plans::PlanCatalog` over a `PlanStore` + `PlanCache` trait pair (the `flags.rs` shape): `SqlxPlanStore` + `InMemoryPlanCache` today, a Redis `PlanCache` behind the same trait later (in-proc caching breaks NFR-10, same caveat as flags). TTL is 5 minutes (`PLAN_CACHE_TTL`) — plans change rarely (owner/admin edits only) and every edit path invalidates explicitly, so staleness after an out-of-band edit is bounded by one TTL. Resolution (`effective_plan` in `services/entitlements.rs`, the single home): the newest live subscription (`trialing`/`active`, `created_at DESC`) overrides the Free default; `past_due` and `canceled` grant nothing; a live subscription whose plan row is gone falls back to Free; a missing Free plan errors `MissingFreePlan` instead of inventing a plan. Entitlements parse in exactly one place (`Entitlements::from_value`, fail-closed).
**Consequences:** A plan edit is visible to resolution within 5 minutes at worst, immediately when the edit goes through the admin API (which invalidates). Two processes can disagree about the plan for up to one TTL — acceptable for a snapshot read (the quota middleware re-checks at job-create time). The profile, the middleware, and the quota snapshot all read through `effective_plan` + `Entitlements::from_value`, so they cannot disagree about what a plan grants. If the Redis cache ever lands, the TTL stays 5 minutes and only the `PlanCache` impl changes.

## ADR-0026 — Concurrency denial is PF-3008; the quota pre-check reads the durable snapshot (2026-11-15, Phase 1)
**Context:** P1-051's spec says the job-create pre-check covers "images + video seconds + concurrency slot" and names only PF-3001/3002 for the denials. The kit's taxonomy has no PF code for a per-user concurrency denial: PF-3005 (`queue_full`) is the system-wide queue signal ("the system is busy; retry shortly" — no upgrade hint), and PF-3003/3004/3006/3007 are taken. Separately, two module docs disagreed about what the pre-check reads: P1-050's `usage.rs` said the middleware reads the Redis day-hash, while the entitlements service doc said it must reuse `quota_snapshot_for_plan` and never re-derive from Redis.
**Decision:** (1) The concurrency denial is a new core variant `QuotaConcurrencyExceeded` → PF-3008 (the next free PF-3xxx slot), 429, title `quota_concurrency_exceeded`, detail "concurrency limit reached; upgrade your plan for more" — the FR-P-06 upgrade hint, matching PF-3001/3002. PF-3005 is not reused. (2) The pre-check reads the durable snapshot (`effective_plan` + `quota_snapshot_for_plan`), not the Redis hash — the snapshot is the source the `/v1/me` quota agrees with by construction, and it matches the kit's DB-seeding pattern (a Redis read would not see DB-seeded usage). The P1-050 doc sentence is corrected in the P1-051 commit. The Redis hash stays the metering hot path for `record`; the atomic check-and-record lands with real job creation in Phase 2.
**Consequences:** The error-contract range test (429 → PF-3xxx) already admits PF-3008; the exact-value table in `crates/core/src/error.rs` pins it. The pre-check's decision and the profile snapshot can only disagree if the plan changes between the two reads (a point-in-time snapshot, re-checked at job-create time). A future Redis-reading fast path, if ever wanted, must prove agreement with the snapshot first — it may not silently replace the DB read.

## ADR-0027 — The quota snapshot's UTC day comes from the app clock, never `Utc::now()` (2026-11-16, Phase 1)
**Context:** P1-057's spec names the UTC reset as a behavior the entitlement suite must prove through the HTTP layer — a Free user denied at 23:59 must be allowed again past midnight. `UsageMeter` already follows the rule "never `Utc::now()` in the service" (its day comes from the injected `Clock`, so the meter-level boundary test freezes time), but `quota_snapshot_for_plan` — the read the profile AND the quota pre-check both use — took its day from `chrono::Utc::now()` directly. A frozen clock could move the meter but not the snapshot, so the reset was untestable end to end.
**Decision:** `quota_snapshot_for_plan` takes the UTC day as a parameter; `precheck` takes it too. The state-level wrappers pass the app clock's day (`state.clock.now().date_naive()`): `precheck_for_create`, `snapshot_for_user`, and both profile call sites (`get_profile`, `patch_profile`). In production the clock is the `SystemClock`, so behavior is unchanged; in tests a `ManualClock` moves the gate, the profile, and the meter together.
**Consequences:** The quota day is now testable without waiting for midnight, and the three quota readers (gate, profile, meter) can no longer disagree about which day it is. Any future quota reader must take its day from the app clock the same way — a fresh `Utc::now()` in a quota path is a bug, not a shortcut. The admin user search (`services/admin.rs`) still reads `Utc::now()` directly for its per-user "today" column; it is a read-only admin view, not a quota decision, and is out of scope for this ticket.

## ADR-0028 — `BillingProvider` is `dyn`-compatible via `async-trait`; `map_webhook` is sync/pure and returns `Option` (2026-11-16, Phase 1)
**Context:** P1-059's spec names the trait's verbs (create_checkout, create_portal, fetch_subscription, map_webhook to DomainEvent, customer ops) and FR-P-05 demands a Razorpay adapter behind a feature flag without touching core code. Two shapes were possible: the codebase's `PlanStore` pattern (native `async fn` in the trait + generics, e.g. `PlanCatalog<S, C>`) or a `dyn`-compatible trait behind `Arc`. The provider is chosen at runtime from config (Stripe now, Razorpay behind a flag), and `AppState` already holds `Arc<dyn Clock>` — the same shape.
**Decision:** (1) The trait uses `#[async_trait]` (0.1.92, already in the lockfile as a transitive dependency, promoted to a direct workspace dep in this commit) so `AppState` can hold `Arc<dyn BillingProvider>` with no type parameter infecting handlers. Native `async fn` + generics was rejected: it would make the trait non-`dyn`-compatible and force `AppState<P: BillingProvider>`. (2) `map_webhook` is sync and pure (parse only, no I/O) and returns `Option<DomainEvent>`: `None` means a well-formed event type the app ignores — the handler answers 200, never an error, so the provider stops retrying. Malformed payloads fail `BillingError::InvalidPayload`; unknown statuses fail closed (`UnknownStatus`, never coerced to `active`). (3) `verify_webhook_signature` is on the trait (sync, raw body + header) so the webhook handler stays provider-agnostic; FR-P-04 idempotency (the event table) lives in the handler, not the trait. (4) `list_invoices` is on the trait now (FR-P-03 + the api-spec `GET /v1/billing/invoices` route) to avoid a breaking trait change later. (5) `DomainEvent` carries ids + status only; the handler resolves the plan from our own catalog — the provider never tells us what a user is entitled to.
**Consequences:** P1-060 implements the trait for Stripe (async-stripe, test mode enforced) and wires `Arc<dyn BillingProvider>` into `AppState`; the Razorpay adapter lands behind its flag after it, with no core-code change. The trait's swap-ability is proven by the `FakeProvider` test (`same_caller_code_works_for_either_provider`): identical caller code against a Stripe double and a Razorpay double.

## ADR-0029 — The products/prices sync is adapter-local over a `CatalogProvider` trait; the trait stays narrow (2026-11-16, Phase 1)
**Context:** P1-061 needs products/prices sync (create product, create recurring monthly price, archive the old price on drift). Two shapes were possible: extend `BillingProvider` with product/price methods, or keep the sync adapter-local behind a small internal trait. The P1-059 trait is a narrow provider-agnostic contract (ADR-0028); products/prices are Stripe-shaped — Razorpay's equivalent is a "plan" with a different API — and no Razorpay adapter exists to implement the extension.
**Decision:** (1) The sync lives in `crates/billing/src/sync.rs`, generic over an internal `CatalogProvider` trait (list/create product, list/create/archive price), implemented for `StripeAdapter` in `stripe.rs`; `BillingProvider` is untouched. (2) The engine's rules: products matched by `detag_plan_code` metadata (never by display name); ₹0 plans skipped; prices immutable — drift creates a new recurring monthly price and archives the old active one; a plan with no configured price adopts an already-matching active price; per-plan failures are recorded and the sync continues; only a product-list failure aborts. (3) The report (`CatalogDriftReport`, one line per plan + counts) is the ticket's AC — returned by the admin endpoint as JSON, and its `price_id_updates()` is what the caller persists to `plans.stripe_price_id`. (4) The manual trigger is `POST /v1/admin/billing/catalog-sync` (admin only, runs inline, audited as `admin.billing.catalog_synced`); the nightly schedule is P1-082's, and the worker's `catalog_sync` kind is a stub until the worker gains a provider + pool.
**Consequences:** A Razorpay catalog sync later needs only a second `CatalogProvider` implementation — no trait change, no engine change. The Stripe catalog legs are untested live (ASSUMPTION-024 clause 6); the engine is proven by `FakeCatalog` tests. A new PF code lands with this ticket: `PF-5005` (`BillingNotConfigured`, 503) for billing endpoints when no provider key is configured.

## ADR-0030 — Checkout: provider in `AppState`, idempotency in the `idempotency_keys` table, URLs from `PF_PUBLIC_BASE_URL` (2026-11-17, Phase 1)
**Context:** P1-062's spec says "auth, plan from body, customer reuse, success/cancel URLs from config; idempotency honored" without naming where the provider lives, how idempotency is stored, or what the URLs are. ADR-0028 anticipated `Arc<dyn BillingProvider>` in `AppState` but P1-060/P1-061 never wired it (the sync builds its own adapter per call); the `idempotency_keys` table exists since migration 20261112065339 with no user; and the console pages the URLs point at do not exist yet (Phase 4).
**Decision:** (1) `AppState` holds `billing: Option<DynBillingProvider>`, built once at boot from the Stripe key (`allow_live = false` always) — `None` when no real key is configured (empty or the dev placeholder), with a warn logged when a configured key fails construction; a missing key never fails boot, and billing endpoints answer 503 `PF-5005`. The `BillingProvider` trait gains a `Debug` supertrait (the `Clock` precedent) so `AppState` keeps deriving `Debug`; the Stripe adapter's hand-written `Debug` already prints nothing. Tests replace the provider via `AppState::with_billing_provider` (the `with_clock` pattern) and a `TestApp` constructor that threads it through. The catalog sync keeps building its own `StripeAdapter` per call: it needs the adapter specifically (its `CatalogProvider` impl), not the shared trait object. (2) Idempotency is the `idempotency_keys` table, not a Stripe-side key: the stored envelope is `{"request": <canonical request JSON>, "response": <the checkout session JSON>}` — the canonical request is endpoint + user id + plan code, compared by exact JSON equality (no hash function to argue about). A replay returns the stored session with no provider call; a different request under the same key is 409 `PF-2011` (the taxonomy's idempotency code). Entries live 24 h (Stripe's checkout-session lifetime); past that the key is dead and the next call is fresh (a stale row is deleted before the new response is stored). A concurrent same-key race can create two Stripe sessions (the loser's insert loses and it replays the winner's response); a sequential retry never does. (3) Success is `{PF_PUBLIC_BASE_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}` and cancel is `{PF_PUBLIC_BASE_URL}/billing/cancel` — the console pages land in Phase 4; until then the URLs are the contract, not live pages. (4) Error mapping: unknown plan 404 `PF-2010`; Free (₹0) or a plan with no Stripe price 422 `PF-2002` on `plan_code` (`not_purchasable`); a configured price Stripe does not know is 500 `PF-5000` (config drift — the catalog sync is the repair); every other provider failure is 500 with no provider message echoed. No audit row: nothing durable is created except the idempotency row — the subscription row and its audit land with the webhook (P1-063/065). No duplicate-purchase guard: upgrade/downgrade timing is P1-069's.
**Consequences:** The checkout happy path is testable end to end with a fake provider, but the Stripe HTTP legs are STILL untested live (no test-mode key on this VM) — the P1-060 note's "first live run is P1-062's integration test, with a test-mode key" is corrected in the test-strategy: the first live run is the endpoint with a real test-mode key, whenever one exists. The `stripe_configured()` check now lives once on `Settings` (P1-061's service and `AppState` share it) instead of a private constant in the sync service. The Razorpay adapter (behind its flag, after P1-062) plugs into the same `AppState` field with no handler change. Expired idempotency rows are deleted lazily on reuse of their key; a nightly sweep (P1-082) can take the rest.

## ADR-0031 — Webhook receiver: verify-then-store, 4xx only on bad signature, dispatch is a seam (2026-11-17, Phase 1)
**Context:** P1-063's spec says "constant-time signature verify, raw-body capture, event table insert (unique event id) for idempotency, then dispatch; 4xx only on bad signature" without naming the error code, the response for a verified-but-unmappable event, or what "dispatch" means before the state machine (P1-064) and the event handlers (P1-065) exist. ADR-0028 put the event table in the handler, not the trait; the `webhook_events` table did not exist yet.
**Decision:** (1) Order is verify → parse → store → dispatch: the raw body is verified with the provider's `verify_webhook_signature` (the real `construct_event`: HMAC-SHA256, constant-time compare, 5-minute timestamp tolerance) before any JSON parse, so a tampered body can never reach the mapping. (2) Bad signature is 400 `PF-2013` (`WebhookSignatureInvalid`, the next free PF-2xxx slot — Stripe's own guidance is 400), and it is the endpoint's ONLY 4xx: billing unconfigured is 503 `PF-5005` (no secret to verify against); a verified-but-unparseable envelope, an ignored type, or an unmappable event (malformed for its type, unknown status) is logged and answered 200, so the provider stops retrying — no retry storm. A replay is 200 with no dispatch and no stamp moved. (3) The ledger is `webhook_events` (UNIQUE `(provider, event_id)`, full-envelope payload, `dispatched_at` stamped once after map + dispatch; 365 d retention like `audit_logs`). (4) Dispatch is the seam, not the application: P1-063 maps the verified event (`map_webhook`, pure) and records the dispatch (stamp + info log); it applies NO subscription change — transition validation is P1-064's and the subscription writes are P1-065's, which read the stored envelopes. The stored envelope is the durable queue, so no event is lost by dispatching later. (5) No auth extractor runs on the route (the signature IS the credential; the API-key matrix row is `Ignored`, not `Allowed`): a key changes nothing.
**Consequences:** The receiver's contract (verify/store/200/replay) is complete and proven against the real adapter through HTTP (8 live tests); the Stripe HTTP legs stay untested live (no test-mode key). The `all_variants` / response-table tests in `error.rs` now include `BillingNotConfigured` too — P1-061 added the variant without listing it, so the "exhaustive" table was one short; this ticket fixes the omission alongside the new variant (39 → 41). P1-065 must not re-implement storage: it applies `DomainEvent`s read from `webhook_events`.

## ADR-0032 — Subscription state machine: pure rules in billing, one guarded transaction for the writes (2026-11-17, Phase 1)
**Context:** P1-064's spec says "trialing/active/past_due/canceled transitions; side effects: entitlement cache flush, emails (welcome, dunning, canceled), audit" without naming where the rules live, what "invalid" means for each pair, or how the side effects stay atomic with the row write. P1-065's handlers need a reusable transition layer, and P1-066's replay/order safety leans on the machine.
**Decision:** (1) The rules are pure in `detag-billing::state_machine` (`transition` over `SubscriptionStatus`, the uploads machine's shape): `trialing → active | past_due | canceled`, `active → past_due | canceled`, `past_due → active | canceled`; `canceled` terminal; no return to `trialing`; same-state is a no-op, not an error. (2) The service (`services/subscription_state.rs`) applies a validated move as a guarded `UPDATE ... WHERE status = $from` inside one transaction with the audit row and the outbox row — a status change never lands without its trail, and two handlers racing the same row cannot both apply (the loser gets PF-5002 and re-reads). (3) The "entitlement cache flush" is `PlanCatalog::invalidate()` after commit — there is no per-user entitlement cache; `effective_plan` reads the row live, so the catalog flush is the whole flush. (4) The mail mapping is welcome on `trialing → active`, dunning on any move to `past_due`, canceled on any move to `canceled`, nothing on recovery — the three templates are transactional (never capped, like the other alerts). (5) The audit action is `billing.subscription.status_changed`, actor `None` / client `"webhook"`, reason the trigger (a webhook event id for P1-065). (6) `apply_domain_event` is the P1-065 entry point: checkout creation and invoice payment map to no target status and are no-ops, never errors.
**Consequences:** P1-065 calls `apply_domain_event` per stored envelope and needs no transition logic of its own; P1-066's replay safety is the machine's no-op plus the ledger's UNIQUE key. The audit actor convention for provider-driven writes is "no user, client webhook" — a future admin-driven transition (if one ever exists) must name its actor explicitly rather than reusing this row shape.

## ADR-0033 — Webhook event handlers: user from `client_reference_id`, plan + status from a fresh fetch, unresolvable is a logged 200, undispatched replays re-dispatch (2026-11-17, Phase 1)
**Context:** P1-065's spec says "`checkout.session.completed`, `invoice.paid`/`payment_failed`, `customer.subscription.updated`/`deleted` mapped; unknown event logged + 200 (no retry storm)" with the AC "mapping table tested", without naming how the handler resolves the checkout's user and plan, what a failed payment does to the row, or what happens when the handler itself fails. Three gaps were open at the ticket's start: `invoice.payment_failed` was unmapped in the Stripe adapter, no handler service existed, and checkout-row creation had no user/plan resolution design (the P1-060 note only said `client_reference_id` "ties the session back to our user").
**Decision:** (1) Mapping: `invoice.payment_failed` maps to a new `DomainEvent::InvoicePaymentFailed { invoice_id, subscription_id: Option<String> }` (same shape as `InvoicePaid`); `target_for_event` sends it to `past_due` — the dunning trigger — and the machine decides whether the row may move there. `CheckoutCompleted` gains `user_id: Option<Uuid>`, read off the session's `client_reference_id` (P1-060 writes our user id there at checkout); absent means the session was not created by our checkout, present-but-not-a-UUID fails mapping (our own bug, loudly). The mapping table is proven twice: the adapter's unit tests (all six mapped types + ignored + malformed) and the handler suite through HTTP. (2) Checkout creation: the handler resolves the user from the event, then calls `fetch_subscription` for the provider-reported status, period end, and item price ids (`SubscriptionState` gains `price_ids`; the adapter expands `items` on retrieve, and the extraction is unit-tested against a deserialized subscription fixture), then resolves the plan as the catalog row whose `stripe_price_id` matches one of those prices. The row and the `billing.subscription.created` audit row land in one transaction; the catalog invalidates after commit (the P1-064 rule). Creation sends NO lifecycle mail: the welcome mail fires on the `trialing → active` transition, and a row created already-`active` is a purchase, not a conversion — a purchase welcome is a product decision, not this ticket's (ASSUMPTION-028). (3) Status and invoice events resolve the row by provider subscription id and apply through `apply_domain_event` (P1-064). Anything *about the event* is a logged no-op answered 200 — no user on the checkout, a subscription the provider no longer knows, a price no plan carries, a row that does not exist yet (an update that arrived before its checkout), a one-off invoice, a move the machine rejects (a stale failure for a canceled row) — the stored envelope stays in the ledger for inspection and the provider stops retrying. Only a genuine failure (the database, or a provider call that errored for a reason other than "unknown subscription") is `Internal` → 500, so Stripe retries. (4) Replay re-dispatch: a redelivery whose ledger row has `dispatched_at` NULL (the first delivery stored the event but its handler 500'd) is dispatched again — the handler is idempotent (existing-row check before insert, same-state no-op, guarded update), so re-dispatch cannot double-apply, and without it a transient failure would lose a paid subscription forever (the provider's retry would be answered as a no-op). A stamped replay stays a no-op with its stamp unmoved. (5) `InvoicePaid` stays a lifecycle no-op: a past-due recovery arrives as a `SubscriptionStatusChanged` to `active` alongside it, and the invoice alone must not move the row.
**Consequences:** The receiver's "200 for every verified delivery" now has one exception — a handler failure is 500 (the route doc and the OpenAPI 500 response say so). The handler's provider call (`fetch_subscription`) is the one Stripe HTTP leg this ticket exercises, and it is proven only against the delegating test double — the live leg stays untested (ASSUMPTION-023). P1-066 owns the remaining replay questions (out-of-order delivery, reprocessing of stored envelopes); the re-dispatch rule here is the narrow fix for "stored but never applied", not a general reprocessing queue.
