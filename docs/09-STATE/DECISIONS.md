## ADR-0018 — PF-5003 `CacheUnavailable`: the Redis failover error (2026-11-12, Phase 0)
**Context:** P0-051 ("failover error mapping to typed errors") found no typed error for Redis failures: `AppError` had only `DatabaseUnavailable` (PF-5001, Postgres) and the redis modules each carried their own `Pool`/`Redis` error variants with no mapping to the API taxonomy. PF-5002 was already taken (`InvalidStateTransition`).
**Decision:** New variant `AppError::CacheUnavailable` — PF-5003, HTTP 503, title `cache_unavailable`, safe detail "the cache is temporarily unavailable". `From` impls map `deadpool_redis::PoolError`, `redis::RedisError`, and the `Pool`/`Redis` variants of `CacheError`/`RateLimitError`/`PubSubError` to it; all other module-error variants map to `Internal` (programmer/caller errors, not failover). **Consequences:** Any Redis outage now surfaces as a typed, PII-free 503. The exhaustive taxonomy tests (34 variants) pin the code. If a future ticket needs to distinguish checkout vs command failures, it must add variants, not match on provider strings.

## ADR-0022 — Argon2id defaults m = 64 MiB, t = 3, p = 4 + rehash-on-login (2026-11-13, Phase 1)
**Context:** P1-027's spec sets the Argon2id defaults to m = 64 MB, t = 3, p = 4 — stronger than the OWASP first choice (m = 19 MiB, t = 2, p = 1) that P1-001 shipped. Every account created before this change carries the old params in its stored PHC hash.
**Decision:** Defaults are m = 65536 KiB, t = 3, p = 4 (`PF_ARGON2_*`, still operator-configurable with the same validated ranges). Old hashes are NOT bulk-rewritten: login upgrades them lazily — on a successful login, when the stored PHC params differ from the current policy, the just-verified password is rehashed with the current params and the new hash is written in the same transaction as the session row (`needs_rehash` in `crates/core/src/password.rs`, wired in `apps/api/src/services/login.rs`). The rehash is opportunistic (a hash failure logs a warn and the login still succeeds) and runs before the transaction so it never holds a pool connection. Measured cost (`cargo bench -p detag-core --bench argon2`, criterion, 10 samples, 2026-11-13 on the 1.5-CPU build VM — an upper bound for the 4-vCPU target VPS): hash ~195 ms and verify ~192 ms at the new defaults, vs ~26 ms / ~29 ms at the old ones. The full note (incl. the 64 MiB-per-hash sizing for login bursts) is in the deploy runbook.
**Consequences:** Every login/register pays ~0.2 s of Argon2id (was ~0.03 s); a pre-P1-027 user pays one extra ~0.2 s hash on their first login after the upgrade. The sync-hash-on-async-worker concern (PERF-001) covers this path too — the rehash follows register's existing inline-hash pattern rather than inventing a new one. If the cost ever needs cutting, the operator lowers `PF_ARGON2_*` in the deployment env; the fleet then converges via rehash-on-login with no migration.

## ADR-0023 — Email send caps enforced at the drain, not at enqueue (2026-11-14, Phase 1)
**Context:** P1-031's spec sets per-recipient hourly caps per template class (verify 3, reset 3, marketing 0) with abuse-log entries on trips. The cap is on SENDS, and mails are enqueued from many services (register, resend, forgot, email-change, lockout, …).
**Decision:** Enforce in the drain (`crates/mailer/src/drain.rs`), the single choke point every queued mail passes through — not at each enqueue site, where a new service would silently dodge the cap. The drain counts sent rows for the recipient's hash + the class's templates in the last hour (`email_outbox::count_sent_recent_for_recipient`; `sent_at` in-window, so queued-but-unsent rows spend nothing) and, on a trip, parks the row (the mail is dropped, not retried into the next hour — its token would be stale by then) and writes an abuse audit row (`email.rate_limit_tripped`, hash + template + class + cap + count, never a raw address, NFR-42). A failed audit insert logs loudly but the row is still parked — enforcement never depends on the log write. A count-query failure is transient (the row is rescheduled, not lost). Caps are operator config (`PF_MAILER_VERIFY_CAP_PER_HOUR` 3 / `PF_MAILER_RESET_CAP_PER_HOUR` 3 / `PF_MAILER_MARKETING_CAP_PER_HOUR` 0). Transactional alerts (`lockout-notice`, `new-login-digest`, …) are never capped — a lockout notice must reach the user precisely when the account is being hammered. Marketing is 0 with no marketing template shipping in v1, so any marketing-class row is parked on sight until the operator deliberately raises the cap.
**Consequences:** The endpoint-level limits stay as the first line (resend 3/hour per user+template, P1-002; forgot 10 burst / 1 per min per account, P1-025); the drain cap is the backstop that catches cross-endpoint combinations (register + resends + an email change adding up to more than 3 verification mails to one address in an hour). A capped mail's caller already got its 204 — the drop is visible only in the audit log and the row's `last_error`, which is the same visibility the lockout-notice path already has.

## ADR-0024 — API keys verify against an `active` owner; suspend does not revoke keys (2026-11-14, Phase 1)
**Context:** P1-034's extractor verifies a `pf_live_*` key by hash lookup and loads the owner. Suspend (`POST /v1/admin/users/{id}/suspend`, P1-008) revokes the user's sessions and blocks the next login — but it touches no `api_keys` row. The JWT path deliberately does NOT check user status in the extractor (P1-008): suspension revokes sessions at suspend time and a pre-suspension access token dies in ≤ 15 min anyway. A key has no expiry, so the same reasoning does not apply — without a status check, a suspended user's key would keep working forever, and the suspension would be bypassable by any key the user minted before it.
**Decision:** The key leg rejects any key whose owner is not `active` — 401 `PF-1001`, indistinguishable from an unknown hash, a revoked key, or a missing owner (the response never says which). The JWT leg is unchanged (still no status check — the ≤ 15 min residual window is P1-008's recorded trade-off). No new revoke-on-suspend behaviour: suspend still does not flip `api_keys` rows — if the owner later wants suspend to revoke keys too, that is a one-line addition to the suspend transaction (revoke keys + audit), and the extractor check stays as the backstop either way. A `deletion_pending` owner likewise cannot use keys (status is not `active`).
**Consequences:** A suspended user's keys stop working at the next request (no residual window, unlike access tokens). Restoring the user (`active` again) restores the keys with no re-mint — the check reads the live row, so there is nothing to undo. Recorded as the P1-034 behaviour in the api-spec extractor paragraph and proven by test (`api_key_of_suspended_user_is_unauthenticated`).

## ADR-0025 — Plan catalog: 5-minute in-memory cache, explicit invalidation; resolution pins trialing/active + newest-wins (2026-11-15, Phase 1)
**Context:** P1-049's spec says "catalog from db (seeded) + cache" without naming the cache or its TTL, and the resolution rule ("subscription override") leaves the edge cases open: which subscription statuses count, what wins when several live subscriptions exist, and what happens when the Free plan is missing. The profile (P1-005) already resolved the plan per request with two DB reads; every later consumer (quota middleware P1-051, `GET /v1/plans`, admin plan editor P1-057) will resolve it too, so the rule needs one home.
**Decision:** The catalog is `detag_core::plans::PlanCatalog` over a `PlanStore` + `PlanCache` trait pair (the `flags.rs` shape): `SqlxPlanStore` + `InMemoryPlanCache` today, a Redis `PlanCache` behind the same trait later (in-proc caching breaks NFR-10, same caveat as flags). TTL is 5 minutes (`PLAN_CACHE_TTL`) — plans change rarely (owner/admin edits only) and every edit path invalidates explicitly, so staleness after an out-of-band edit is bounded by one TTL. Resolution (`effective_plan` in `services/entitlements.rs`, the single home): the newest live subscription (`trialing`/`active`, `created_at DESC`) overrides the Free default; `past_due` and `canceled` grant nothing; a live subscription whose plan row is gone falls back to Free; a missing Free plan errors `MissingFreePlan` instead of inventing a plan. Entitlements parse in exactly one place (`Entitlements::from_value`, fail-closed).
**Consequences:** A plan edit is visible to resolution within 5 minutes at worst, immediately when the edit goes through the admin API (which invalidates). Two processes can disagree about the plan for up to one TTL — acceptable for a snapshot read (the quota middleware re-checks at job-create time). The profile, the middleware, and the quota snapshot all read through `effective_plan` + `Entitlements::from_value`, so they cannot disagree about what a plan grants. If the Redis cache ever lands, the TTL stays 5 minutes and only the `PlanCache` impl changes.

## ADR-0026 — Concurrency denial is PF-3008; the quota pre-check reads the durable snapshot (2026-11-15, Phase 1)
**Context:** P1-051's spec says the job-create pre-check covers "images + video seconds + concurrency slot" and names only PF-3001/3002 for the denials. The kit's taxonomy has no PF code for a per-user concurrency denial: PF-3005 (`queue_full`) is the system-wide queue signal ("the system is busy; retry shortly" — no upgrade hint), and PF-3003/3004/3006/3007 are taken. Separately, two module docs disagreed about what the pre-check reads: P1-050's `usage.rs` said the middleware reads the Redis day-hash, while the entitlements service doc said it must reuse `quota_snapshot_for_plan` and never re-derive from Redis.
**Decision:** (1) The concurrency denial is a new core variant `QuotaConcurrencyExceeded` → PF-3008 (the next free PF-3xxx slot), 429, title `quota_concurrency_exceeded`, detail "concurrency limit reached; upgrade your plan for more" — the FR-P-06 upgrade hint, matching PF-3001/3002. PF-3005 is not reused. (2) The pre-check reads the durable snapshot (`effective_plan` + `quota_snapshot_for_plan`), not the Redis hash — the snapshot is the source the `/v1/me` quota agrees with by construction, and it matches the kit's DB-seeding pattern (a Redis read would not see DB-seeded usage). The P1-050 doc sentence is corrected in the P1-051 commit. The Redis hash stays the metering hot path for `record`; the atomic check-and-record lands with real job creation in Phase 2.
**Consequences:** The error-contract range test (429 → PF-3xxx) already admits PF-3008; the exact-value table in `crates/core/src/error.rs` pins it. The pre-check's decision and the profile snapshot can only disagree if the plan changes between the two reads (a point-in-time snapshot, re-checked at job-create time). A future Redis-reading fast path, if ever wanted, must prove agreement with the snapshot first — it may not silently replace the DB read.

## ADR-0027 — The quota snapshot's UTC day comes from the app clock, never `Utc::now()` (2026-11-16, Phase 1)
**Context:** P1-057's spec names the UTC reset as a behavior the entitlement suite must prove through the HTTP layer — a Free user denied at 23:59 must be allowed again past midnight. `UsageMeter` already follows the rule "never `Utc::now()` in the service" (its day comes from the injected `Clock`, so the meter-level boundary test freezes time), but `quota_snapshot_for_plan` — the read the profile AND the quota pre-check both use — took its day from `chrono::Utc::now()` directly. A frozen clock could move the meter but not the snapshot, so the reset was untestable end to end.
**Decision:** `quota_snapshot_for_plan` takes the UTC day as a parameter; `precheck` takes it too. The state-level wrappers pass the app clock's day (`state.clock.now().date_naive()`): `precheck_for_create`, `snapshot_for_user`, and both profile call sites (`get_profile`, `patch_profile`). In production the clock is the `SystemClock`, so behavior is unchanged; in tests a `ManualClock` moves the gate, the profile, and the meter together.
**Consequences:** The quota day is now testable without waiting for midnight, and the three quota readers (gate, profile, meter) can no longer disagree about which day it is. Any future quota reader must take its day from the app clock the same way — a fresh `Utc::now()` in a quota path is a bug, not a shortcut. The admin user search (`services/admin.rs`) still reads `Utc::now()` directly for its per-user "today" column; it is a read-only admin view, not a quota decision, and is out of scope for this ticket.

## ADR-0028 — `BillingProvider` is `dyn`-compatible via `async-trait`; `map_webhook` is sync/pure and returns `Option` (2026-11-16, Phase 1)
**Context:** P1-059's spec names the trait's verbs (create_checkout, create_portal, fetch_subscription, map_webhook to DomainEvent, customer ops) and FR-P-05 demands a Razorpay adapter behind a feature flag without touching core code. Two shapes were possible: the codebase's `PlanStore` pattern (native `async fn` in the trait + generics, e.g. `PlanCatalog<S, C>`) or a `dyn`-compatible trait behind `Arc`. The provider is chosen at runtime from config (Stripe now, Razorpay behind a flag), and `AppState` already holds `Arc<dyn Clock>` — the same shape.
**Decision:** (1) The trait uses `#[async_trait]` (0.1.92, already in the lockfile as a transitive dependency, promoted to a direct workspace dep in this commit) so `AppState` can hold `Arc<dyn BillingProvider>` with no type parameter infecting handlers. Native `async fn` + generics was rejected: it would make the trait non-`dyn`-compatible and force `AppState<P: BillingProvider>`. (2) `map_webhook` is sync and pure (parse only, no I/O) and returns `Option<DomainEvent>`: `None` means a well-formed event type the app ignores — the handler answers 200, never an error, so the provider stops retrying. Malformed payloads fail `BillingError::InvalidPayload`; unknown statuses fail closed (`UnknownStatus`, never coerced to `active`). (3) `verify_webhook_signature` is on the trait (sync, raw body + header) so the webhook handler stays provider-agnostic; FR-P-04 idempotency (the event table) lives in the handler, not the trait. (4) `list_invoices` is on the trait now (FR-P-03 + the api-spec `GET /v1/billing/invoices` route) to avoid a breaking trait change later. (5) `DomainEvent` carries ids + status only; the handler resolves the plan from our own catalog — the provider never tells us what a user is entitled to.
**Consequences:** P1-060 implements the trait for Stripe (async-stripe, test mode enforced) and wires `Arc<dyn BillingProvider>` into `AppState`; the Razorpay adapter lands behind its flag after it, with no core-code change. The trait's swap-ability is proven by the `FakeProvider` test (`same_caller_code_works_for_either_provider`): identical caller code against a Stripe double and a Razorpay double.

## ADR-0029 — The products/prices sync is adapter-local over a `CatalogProvider` trait; the trait stays narrow (2026-11-16, Phase 1)
**Context:** P1-061 needs products/prices sync (create product, create recurring monthly price, archive the old price on drift). Two shapes were possible: extend `BillingProvider` with product/price methods, or keep the sync adapter-local behind a small internal trait. The P1-059 trait is a narrow provider-agnostic contract (ADR-0028); products/prices are Stripe-shaped — Razorpay's equivalent is a "plan" with a different API — and no Razorpay adapter exists to implement the extension.
**Decision:** (1) The sync lives in `crates/billing/src/sync.rs`, generic over an internal `CatalogProvider` trait (list/create product, list/create/archive price), implemented for `StripeAdapter` in `stripe.rs`; `BillingProvider` is untouched. (2) The engine's rules: products matched by `detag_plan_code` metadata (never by display name); ₹0 plans skipped; prices immutable — drift creates a new recurring monthly price and archives the old active one; a plan with no configured price adopts an already-matching active price; per-plan failures are recorded and the sync continues; only a product-list failure aborts. (3) The report (`CatalogDriftReport`, one line per plan + counts) is the ticket's AC — returned by the admin endpoint as JSON, and its `price_id_updates()` is what the caller persists to `plans.stripe_price_id`. (4) The manual trigger is `POST /v1/admin/billing/catalog-sync` (admin only, runs inline, audited as `admin.billing.catalog_synced`); the nightly schedule is P1-082's, and the worker's `catalog_sync` kind is a stub until the worker gains a provider + pool.
**Consequences:** A Razorpay catalog sync later needs only a second `CatalogProvider` implementation — no trait change, no engine change. The Stripe catalog legs are untested live (ASSUMPTION-024 clause 6); the engine is proven by `FakeCatalog` tests. A new PF code lands with this ticket: `PF-5005` (`BillingNotConfigured`, 503) for billing endpoints when no provider key is configured.

## ADR-0030 — Checkout: provider in `AppState`, idempotency in the `idempotency_keys` table, URLs from `PF_PUBLIC_BASE_URL` (2026-11-17, Phase 1)
**Context:** P1-062's spec says "auth, plan from body, customer reuse, success/cancel URLs from config; idempotency honored" without naming where the provider lives, how idempotency is stored, or what the URLs are. ADR-0028 anticipated `Arc<dyn BillingProvider>` in `AppState` but P1-060/P1-061 never wired it (the sync builds its own adapter per call); the `idempotency_keys` table exists since migration 20261112065339 with no user; and the console pages the URLs point at do not exist yet (Phase 4).
**Decision:** (1) `AppState` holds `billing: Option<DynBillingProvider>`, built once at boot from the Stripe key (`allow_live = false` always) — `None` when no real key is configured (empty or the dev placeholder), with a warn logged when a configured key fails construction; a missing key never fails boot, and billing endpoints answer 503 `PF-5005`. The `BillingProvider` trait gains a `Debug` supertrait (the `Clock` precedent) so `AppState` keeps deriving `Debug`; the Stripe adapter's hand-written `Debug` already prints nothing. Tests replace the provider via `AppState::with_billing_provider` (the `with_clock` pattern) and a `TestApp` constructor that threads it through. The catalog sync keeps building its own `StripeAdapter` per call: it needs the adapter specifically (its `CatalogProvider` impl), not the shared trait object. (2) Idempotency is the `idempotency_keys` table, not a Stripe-side key: the stored envelope is `{"request": <canonical request JSON>, "response": <the checkout session JSON>}` — the canonical request is endpoint + user id + plan code, compared by exact JSON equality (no hash function to argue about). A replay returns the stored session with no provider call; a different request under the same key is 409 `PF-2011` (the taxonomy's idempotency code). Entries live 24 h (Stripe's checkout-session lifetime); past that the key is dead and the next call is fresh (a stale row is deleted before the new response is stored). A concurrent same-key race can create two Stripe sessions (the loser's insert loses and it replays the winner's response); a sequential retry never does. (3) Success is `{PF_PUBLIC_BASE_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}` and cancel is `{PF_PUBLIC_BASE_URL}/billing/cancel` — the console pages land in Phase 4; until then the URLs are the contract, not live pages. (4) Error mapping: unknown plan 404 `PF-2010`; Free (₹0) or a plan with no Stripe price 422 `PF-2002` on `plan_code` (`not_purchasable`); a configured price Stripe does not know is 500 `PF-5000` (config drift — the catalog sync is the repair); every other provider failure is 500 with no provider message echoed. No audit row: nothing durable is created except the idempotency row — the subscription row and its audit land with the webhook (P1-063/065). No duplicate-purchase guard: upgrade/downgrade timing is P1-069's.
**Consequences:** The checkout happy path is testable end to end with a fake provider, but the Stripe HTTP legs are STILL untested live (no test-mode key on this VM) — the P1-060 note's "first live run is P1-062's integration test, with a test-mode key" is corrected in the test-strategy: the first live run is the endpoint with a real test-mode key, whenever one exists. The `stripe_configured()` check now lives once on `Settings` (P1-061's service and `AppState` share it) instead of a private constant in the sync service. The Razorpay adapter (behind its flag, after P1-062) plugs into the same `AppState` field with no handler change. Expired idempotency rows are deleted lazily on reuse of their key; a nightly sweep (P1-082) can take the rest.

## ADR-0031 — Webhook receiver: verify-then-store, 4xx only on bad signature, dispatch is a seam (2026-11-17, Phase 1)
**Context:** P1-063's spec says "constant-time signature verify, raw-body capture, event table insert (unique event id) for idempotency, then dispatch; 4xx only on bad signature" without naming the error code, the response for a verified-but-unmappable event, or what "dispatch" means before the state machine (P1-064) and the event handlers (P1-065) exist. ADR-0028 put the event table in the handler, not the trait; the `webhook_events` table did not exist yet.
**Decision:** (1) Order is verify → parse → store → dispatch: the raw body is verified with the provider's `verify_webhook_signature` (the real `construct_event`: HMAC-SHA256, constant-time compare, 5-minute timestamp tolerance) before any JSON parse, so a tampered body can never reach the mapping. (2) Bad signature is 400 `PF-2013` (`WebhookSignatureInvalid`, the next free PF-2xxx slot — Stripe's own guidance is 400), and it is the endpoint's ONLY 4xx: billing unconfigured is 503 `PF-5005` (no secret to verify against); a verified-but-unparseable envelope, an ignored type, or an unmappable event (malformed for its type, unknown status) is logged and answered 200, so the provider stops retrying — no retry storm. A replay is 200 with no dispatch and no stamp moved. (3) The ledger is `webhook_events` (UNIQUE `(provider, event_id)`, full-envelope payload, `dispatched_at` stamped once after map + dispatch; 365 d retention like `audit_logs`). (4) Dispatch is the seam, not the application: P1-063 maps the verified event (`map_webhook`, pure) and records the dispatch (stamp + info log); it applies NO subscription change — transition validation is P1-064's and the subscription writes are P1-065's, which read the stored envelopes. The stored envelope is the durable queue, so no event is lost by dispatching later. (5) No auth extractor runs on the route (the signature IS the credential; the API-key matrix row is `Ignored`, not `Allowed`): a key changes nothing.
**Consequences:** The receiver's contract (verify/store/200/replay) is complete and proven against the real adapter through HTTP (8 live tests); the Stripe HTTP legs stay untested live (no test-mode key). The `all_variants` / response-table tests in `error.rs` now include `BillingNotConfigured` too — P1-061 added the variant without listing it, so the "exhaustive" table was one short; this ticket fixes the omission alongside the new variant (39 → 41). P1-065 must not re-implement storage: it applies `DomainEvent`s read from `webhook_events`.

## ADR-0032 — Subscription state machine: pure rules in billing, one guarded transaction for the writes (2026-11-17, Phase 1)
**Context:** P1-064's spec says "trialing/active/past_due/canceled transitions; side effects: entitlement cache flush, emails (welcome, dunning, canceled), audit" without naming where the rules live, what "invalid" means for each pair, or how the side effects stay atomic with the row write. P1-065's handlers need a reusable transition layer, and P1-066's replay/order safety leans on the machine.
**Decision:** (1) The rules are pure in `detag-billing::state_machine` (`transition` over `SubscriptionStatus`, the uploads machine's shape): `trialing → active | past_due | canceled`, `active → past_due | canceled`, `past_due → active | canceled`; `canceled` terminal; no return to `trialing`; same-state is a no-op, not an error. (2) The service (`services/subscription_state.rs`) applies a validated move as a guarded `UPDATE ... WHERE status = $from` inside one transaction with the audit row and the outbox row — a status change never lands without its trail, and two handlers racing the same row cannot both apply (the loser gets PF-5002 and re-reads). (3) The "entitlement cache flush" is `PlanCatalog::invalidate()` after commit — there is no per-user entitlement cache; `effective_plan` reads the row live, so the catalog flush is the whole flush. (4) The mail mapping is welcome on `trialing → active`, dunning on any move to `past_due`, canceled on any move to `canceled`, nothing on recovery — the three templates are transactional (never capped, like the other alerts). (5) The audit action is `billing.subscription.status_changed`, actor `None` / client `"webhook"`, reason the trigger (a webhook event id for P1-065). (6) `apply_domain_event` is the P1-065 entry point: checkout creation and invoice payment map to no target status and are no-ops, never errors.
**Consequences:** P1-065 calls `apply_domain_event` per stored envelope and needs no transition logic of its own; P1-066's replay safety is the machine's no-op plus the ledger's UNIQUE key. The audit actor convention for provider-driven writes is "no user, client webhook" — a future admin-driven transition (if one ever exists) must name its actor explicitly rather than reusing this row shape.

## ADR-0033 — Webhook event handlers: user from `client_reference_id`, plan + status from a fresh fetch, unresolvable is a logged 200, undispatched replays re-dispatch (2026-11-17, Phase 1)
**Context:** P1-065's spec says "`checkout.session.completed`, `invoice.paid`/`payment_failed`, `customer.subscription.updated`/`deleted` mapped; unknown event logged + 200 (no retry storm)" with the AC "mapping table tested", without naming how the handler resolves the checkout's user and plan, what a failed payment does to the row, or what happens when the handler itself fails. Three gaps were open at the ticket's start: `invoice.payment_failed` was unmapped in the Stripe adapter, no handler service existed, and checkout-row creation had no user/plan resolution design (the P1-060 note only said `client_reference_id` "ties the session back to our user").
**Decision:** (1) Mapping: `invoice.payment_failed` maps to a new `DomainEvent::InvoicePaymentFailed { invoice_id, subscription_id: Option<String> }` (same shape as `InvoicePaid`); `target_for_event` sends it to `past_due` — the dunning trigger — and the machine decides whether the row may move there. `CheckoutCompleted` gains `user_id: Option<Uuid>`, read off the session's `client_reference_id` (P1-060 writes our user id there at checkout); absent means the session was not created by our checkout, present-but-not-a-UUID fails mapping (our own bug, loudly). The mapping table is proven twice: the adapter's unit tests (all six mapped types + ignored + malformed) and the handler suite through HTTP. (2) Checkout creation: the handler resolves the user from the event, then calls `fetch_subscription` for the provider-reported status, period end, and item price ids (`SubscriptionState` gains `price_ids`; the adapter expands `items` on retrieve, and the extraction is unit-tested against a deserialized subscription fixture), then resolves the plan as the catalog row whose `stripe_price_id` matches one of those prices. The row and the `billing.subscription.created` audit row land in one transaction; the catalog invalidates after commit (the P1-064 rule). Creation sends NO lifecycle mail: the welcome mail fires on the `trialing → active` transition, and a row created already-`active` is a purchase, not a conversion — a purchase welcome is a product decision, not this ticket's (ASSUMPTION-028). (3) Status and invoice events resolve the row by provider subscription id and apply through `apply_domain_event` (P1-064). Anything *about the event* is a logged no-op answered 200 — no user on the checkout, a subscription the provider no longer knows, a price no plan carries, a row that does not exist yet (an update that arrived before its checkout), a one-off invoice, a move the machine rejects (a stale failure for a canceled row) — the stored envelope stays in the ledger for inspection and the provider stops retrying. Only a genuine failure (the database, or a provider call that errored for a reason other than "unknown subscription") is `Internal` → 500, so Stripe retries. (4) Replay re-dispatch: a redelivery whose ledger row has `dispatched_at` NULL (the first delivery stored the event but its handler 500'd) is dispatched again — the handler is idempotent (existing-row check before insert, same-state no-op, guarded update), so re-dispatch cannot double-apply, and without it a transient failure would lose a paid subscription forever (the provider's retry would be answered as a no-op). A stamped replay stays a no-op with its stamp unmoved. (5) `InvoicePaid` stays a lifecycle no-op: a past-due recovery arrives as a `SubscriptionStatusChanged` to `active` alongside it, and the invoice alone must not move the row.
**Consequences:** The receiver's "200 for every verified delivery" now has one exception — a handler failure is 500 (the route doc and the OpenAPI 500 response say so). The handler's provider call (`fetch_subscription`) is the one Stripe HTTP leg this ticket exercises, and it is proven only against the delegating test double — the live leg stays untested (ASSUMPTION-023). P1-066 owns the remaining replay questions (out-of-order delivery, reprocessing of stored envelopes); the re-dispatch rule here is the narrow fix for "stored but never applied", not a general reprocessing queue.

## ADR-0034 — Upgrade/downgrade proration: pure math, same endpoint, downgrade as a durable row, applier on the webhook path (2026-11-18, Phase 1)
**Context:** P1-069's spec says "Upgrade via checkout with immediate proration; downgrade schedules at period end; entitlement switch timing documented + tested" without naming where the proration math lives, what the checkout endpoint returns for a downgrade, where the schedule is stored, or what applies it. The checkout endpoint (P1-062) had no duplicate-purchase guard at all — deliberately deferred here — and the `subscriptions` row stores only `current_period_end`, no period start.
**Decision:** (1) The math is pure in `detag-billing::proration` (`classify` by catalog amount, `preview`): an upgrade is effective now with credit = old × remaining/period and charge = new × remaining/period (whole seconds, each leg truncated toward zero — at most one paise per leg); a downgrade is effective at the period end with all legs zero (nothing is charged now). The period start is derived, not stored: one calendar month before the period end (all catalog plans are monthly, ASSUMPTION-032; a month with no matching day clamps to its last day). A row with no period end has no period to prorate — the zero preview (upgrade effective now, downgrade effective now). The preview is what the buyer is shown; the provider's invoice is authoritative — this ticket does not re-implement Stripe's invoice. (2) One endpoint, two statuses: `POST /v1/billing/checkout` returns 200 with `{id, url, proration}` for a purchase or an upgrade and 202 with `{scheduled: true, plan_code, from_plan_code, effective_at, proration}` for a downgrade — no new route, so the route table, the API-key matrix, and the OpenAPI handler counts do not move (the 202 is a new response on the existing path). The same plan is 422 `not_purchasable` ("already subscribed to this plan"); a second pending change for the same subscription is 409 `PF-2011` (the partial UNIQUE index is the guard). Idempotency stores the wire body, so a replay returns the exact body and status the first call returned. (3) The downgrade's durable state is `scheduled_plan_changes` (user, subscription, from/to plan, `effective_at`, `scheduled` → `applied`/`canceled`; one pending change per subscription; rows never deleted). (4) The applier lives in the webhook handler path (`services/plan_changes.rs`, called from `apply_to_subscription` after any successfully applied event): a change is due when the clock reaches `effective_at` OR the event's period end passes it — either signal is honest evidence the period rolled. Applying is one transaction: a paid target moves the row's plan (`set_plan_guarded`, live statuses only), a Free target cancels the row (there is no Free subscription row to move to), the change closes as `applied`, and a `billing.subscription.plan_changed` audit row lands with it; a row that no longer grants a plan makes the change moot (closed as `canceled`, no audit). The catalog invalidates after commit (the P1-064 rule). (5) The applier never calls the provider, and the upgrade's provider-side supersede is not built here: the checkout writes the live subscription id to the session's `subscription_data.metadata` (`detag_upgrade_from`) so a later ticket can cancel the old row when the new checkout completes; until then the newest-live-wins rule (P1-049) makes the upgrade effective and the old row stays live-but-stale (ASSUMPTION-032). The provider-side price switch for a downgrade (Stripe subscription schedule / cancel at period end) is a follow-up for the same reason: it cannot be proven with no test-mode key, and a wrong half-measure would re-price a live subscription mid-period.
**Consequences:** The entitlement switch timing is proven end to end (7 proration live tests + 2 applier live tests, incl. the AC): an upgrade previews half-period numbers and returns the session, a downgrade 202s with the durable row, and the roll event flips the row to the target plan (or cancels it for Free) with exactly one audit row. The Stripe HTTP legs stay untested live (ASSUMPTION-023). Follow-ups: the webhook supersede (read `detag_upgrade_from` on `checkout.session.completed`), the provider-side downgrade switch, and a scheduled-change cancel/replace endpoint (P1-071 owns cancel policy).

## ADR-0035 — Dunning: day 0 IS the past_due mail; days 3/7 are reminder mails from a policy job; day 14 cancels the subscription (2026-11-18, Phase 1)
**Context:** P1-070's spec says "past_due sequence (day 0/3/7), retry window, suspend-at-day-14 policy job (configurable), audited" without naming what day 0 is, what identifies a day-3/7 subscription, what the retry window means, what day 14 suspends, or what the audit actions are. P1-064/ADR-0032 already mails `subscription-dunning` on any move to `past_due`; P1-082 owns the nightly schedule, so this ticket delivers the invocable job + its tests, not the scheduler.
**Decision:** (1) DAY 0 IS THE P1-064 MAIL: the move to `past_due` enqueues `subscription-dunning` once — there is no additional day-0 mail from the dunning job, so a subscription can never be double-dunned on the day it fails. The job handles days 3/7/14 only. To make that provable the move also stamps the dunning state on the row (see (2)). (2) DUNNING STATE LIVES ON THE ROW, NOT THE AUDIT TRAIL: two new columns on `subscriptions` — `past_due_since TIMESTAMPTZ` (when the row entered `past_due`, from the app clock) and `dunning_step SMALLINT` (the last reminder step mailed: 0 = day 0, 3 = day 3, 7 = day 7), guarded by a DB CHECK `(status = 'past_due') = (past_due_since IS NOT NULL)` so the invariant is real, not a convention. The audit trail stays the trail: deriving "days past due" from audit rows would need a per-row audit query, and deriving "which reminders were sent" from outbox rows whose payload carries no subscription id — both fragile where a column is one indexed scan. The move into `past_due` sets both (via `apply_transition`, which owns every status move); any move OUT of `past_due` clears both, so recovery resets the sequence. A second failed invoice while already past due is a same-state no-op (P1-064) — days count from the FIRST failure, never the latest. Existing past_due rows backfill `past_due_since = updated_at` (exact: `set_status_guarded` bumps `updated_at` on every status move, so for a past_due row it IS the entry time) with step 0. (3) DAYS 3/7 ARE SEPARATE TEMPLATES: `subscription-dunning-day3` / `subscription-dunning-day7`, transactional (never capped, ADR-0023), with escalating copy hardcoded in each template (the day is the template, not a payload variable — the mailer snapshot context carries no `day`). Reusing `subscription-dunning` three times would send the identical text on days 0/3/7; the point of the sequence is escalating urgency. Payload stays `{user_id, plan_code}` like the day-0 mail; the template name is the discriminator in the outbox. (4) THE RETRY WINDOW IS THE HEALING WINDOW, NOT A CHARGE RETRY: the provider retries the failed charge on its own schedule (Stripe Smart Retries — we neither control nor observe it); the job NEVER re-attempts a charge and makes NO provider call at all. "Retry window" means the window in which a successful payment heals the sequence: from the failed payment until the day-14 cancel, an `invoice.paid` / status → `active` recovery clears the dunning state and stops all further reminders, and the user is Pro again (P1-049). After day 14 the row is canceled and a later payment does NOT resurrect it — the user checks out again (a new row). (5) DAY 14 SUSPENDS THE SUBSCRIPTION, NOT THE ACCOUNT: the job cancels the subscription row (`past_due → canceled` through the state machine, so the `subscription-canceled` mail and the `billing.subscription.status_changed` audit land with it, reason `dunning-day-14`). Suspending the whole user account (P1-008 admin suspend) would lock the user out of free-tier access too — disproportionate for a failed card — while canceling the subscription revokes paid entitlements immediately via `effective_plan` (P1-049), which is the actual enforcement; the user keeps their account and data and can re-subscribe. (6) CONFIG: `PF_BILLING_DUNNING_ENABLED` (bool, default true — the kill-switch), `PF_BILLING_DUNNING_DAY3_DAYS` (default 3), `PF_BILLING_DUNNING_DAY7_DAYS` (default 7), `PF_BILLING_DUNNING_SUSPEND_DAYS` (default 14); validated `1 <= day3 < day7 < suspend`. (7) AUDIT: each reminder writes `billing.subscription.dunning_reminder` (actor `None`, client `"dunning"`, before/after `{dunning_step, day}`, reason `dunning-day-N`) in the same transaction as its outbox row and its guarded step bump — a reminder never lands without its trail, the P1-064 rule. The day-14 cancel reuses `billing.subscription.status_changed` (it IS a status change). (8) THE JOB: `services/dunning.rs::run_dunning(state, config)` — one scan of `status = 'past_due'` rows, whole days since `past_due_since` (floor, app clock), per-row outcome (reminded / suspended / skipped / error), per-row failures logged + counted without aborting the sweep (the P1-061 per-plan-failure precedent). A re-run the same day is a no-op: the step guard makes each reminder exactly-once. The worker gains `JobKind::Dunning` (`"dunning"`) as a stub (the catalog_sync precedent — the worker has no pool/clock yet; P1-082 owns the schedule). (9) CREATION AS PAST_DUE MAILS DAY 0: a checkout whose provider-reported status is already `past_due` enqueues the day-0 `subscription-dunning` mail in the same transaction as the row (ADR-0033's "creation sends no lifecycle mail" was about the welcome mail for an active purchase — a past-due creation IS a failed payment, and saying nothing for three days would be the hole in "day 0 IS that mail").
**Consequences:** The sequence is proven end to end with a frozen clock (the AC): day-0 mail on the move, day-3 mail at +3d, day-7 at +7d, cancel at +14d, re-runs send nothing twice, recovery mid-sequence stops it and clears the state. The Stripe HTTP legs stay untested live (ASSUMPTION-023) — the job proves itself against seeded rows with no provider call at all. Follow-ups: the P1-082 nightly schedule that enqueues `dunning`, and the provider-side price switch for downgrades (ASSUMPTION-032) — unrelated.

## ADR-0036 — Refund/cancel policy: support cancel is an admin billing write; local cancel only; refund guidance is a dashboard link; the ToS snippet rides the response (2026-11-18, Phase 1)
**Context:** P1-071's spec says "Support-facing: immediate cancel (no proration) + refund guidance (Stripe dashboard) - audited note; ToS policy snippet" without naming who may call the cancel, what "immediate" does to the row versus P1-069's scheduled downgrade-to-Free cancel, where the refund guidance lives, what the audited-note action is, or where the ToS snippet lives. ADR-0032's consequence anticipated this ticket exactly: "a future admin-driven transition (if one ever exists) must name its actor explicitly rather than reusing this row shape" — and ADR-0034's consequence names P1-071 as the owner of cancel policy ("a scheduled-change cancel/replace endpoint (P1-071 owns cancel policy)").
**Decision:** (1) IMMEDIATE MEANS NOW, ON OUR ROW: `POST /v1/admin/billing/subscriptions/{id}/cancel` moves the row to `canceled` immediately through the P1-064 machine (`trialing`/`active`/`past_due → canceled`, guarded write), `cancel_at_period_end` cleared to `false`, `current_period_end` kept as the historical record of when the paid period would have ended. P1-069's downgrade-to-Free is the opposite timing: the row stays live until the period end and only then cancels. Same-state (already canceled) is a 200 no-op with `changed: false` — the machine's no-op precedent (P1-064/066), not an error. A pending scheduled plan change for the subscription is mooted (closed as `canceled`) right after the cancel commits — the P1-069 applier's moot precedent, so a later period roll cannot resurrect a canceled row's downgrade. (2) ADMIN ONLY — SUPPORT STAYS READ-ONLY: "support-facing" means the endpoint serves the support workflow, but support is read-only per FR-A-07 and the authz matrix ("every write admits admin only") — no new write role for support. The endpoint reuses the existing `AdminBillingWrite` capability (`admin.billing.write`, the catalog-sync capability): support gets 403 `PF-1002`, an API key 403, anonymous 401. (3) NO PROVIDER CALL: the endpoint cancels OUR row only — no Stripe cancel call and no refund API call. The provider-side cancel leg does not exist on the `BillingProvider` trait, cannot be proven with no test-mode key (ASSUMPTION-023), and the spec itself puts money actions in the dashboard; the provider-side cancel is a follow-up (ASSUMPTION-034). Until it lands, the response's refund guidance tells support to cancel the Stripe subscription in the dashboard too, so billing stops. (4) REFUND GUIDANCE LIVES IN THE RESPONSE: `refund_guidance: { dashboard_url, note }` — `dashboard_url` is `https://dashboard.stripe.com/subscriptions/{provider_subscription_id}` (the subscriptions list URL when the row carries no provider id); the note says refunds are issued in the dashboard on the latest invoice/payment, never by this API. No refund endpoint is exposed. (5) THE AUDITED NOTE REUSES `billing.subscription.status_changed`: the machine's canonical action, with the actor naming the admin explicitly (`actor_user_id` = the calling admin, `actor_client` = `"admin"`) and `reason` = the support note — a required `ReasonRequest` (1–500 chars, the P1-008 suspend precedent). The actor is what distinguishes a support cancel from a webhook cancel in the audit viewer; the handler marks `AuditHandled` so the P1-046 middleware stands down and the row exists exactly once (also on the no-op, which deliberately writes none). `audit_action_for` / `audit_target_type_for` gain the route (`billing.subscription.status_changed` / `subscription`) so the route-metadata table stays complete. (6) THE TOS SNIPPET IS A CONST, SURFACED TWICE: the canonical policy text lives once as a const in the service, is returned in the response as `policy`, and is quoted verbatim in `docs/06-DELIVERY/10-pricing-config.md` under "Refund & cancel policy". No separate policy GET endpoint — a dedicated read surface is a follow-up if the console needs one. (7) MAIL: the move to `canceled` sends the existing `subscription-canceled` mail through `apply_transition` — no new template; the customer is told the same way a webhook cancel tells them.
**Consequences:** The flow is proven end to end through the real HTTP layer (the AC): admin cancel flips the row + audit + mail + mooted change; a second cancel is a no-op with no second audit; support/user/key/anonymous are denied; an unknown id is 404; a past_due row cancels with its dunning state cleared. The Stripe HTTP legs stay untested live (ASSUMPTION-023) — the endpoint makes no provider call at all, so there is nothing live to prove on this ticket. Follow-ups: the provider-side cancel leg (trait method + Stripe impl + the dashboard step it replaces), the scheduled-change cancel/replace endpoint for buyers (ASSUMPTION-032 clause 5 names the gap), and a policy read endpoint if the console needs one.

## ADR-0037 — Stripe suite: consolidate P1-059–P1-071 in one regression file; the two idempotency layers are proved separately (2026-11-18, Phase 1)
**Context:** P1-072's spec names four behaviours — test-clock lifecycle, signature tamper, replay, idempotency, proration math units — but each already has a home: the adapter's units (P1-060), the receiver (P1-063), the handlers (P1-065/066), the checkout (P1-062), the proration math (P1-069). What no suite proved was the wiring TOGETHER: a subscription's whole life through signed deliveries on a test clock, the signature tolerance through the HTTP layer, and the difference between the ledger's event-id dedup and the state machine's same-state no-op.
**Decision:** (1) ONE FILE, `apps/api/tests/stripe_suite.rs`, holds the consolidation — 5 live tests, no new product code, no new route, no migration. (2) THE LIFECYCLE IS THE AC: trial → active → past_due → canceled in one test, with the frozen clock advanced between steps and the audit trail asserted as the four statuses in order; a replay of the terminal deletion is the cap. Trialing grants Pro from day one (`active_for_user` matches `trialing` — the P1-064 live-status rule, corrected in the test, not the product). (3) THE TWO IDEMPOTENCY LAYERS ARE SEPARATE TESTS: replay-with-a-different-body proves the ledger dedups on the event id before dispatch (the original payload is kept); duplicate-payment-failed proves the state machine makes the domain effect idempotent when the ledger legitimately sees two distinct events. (4) PRORATION EDGES GO TO THE UNIT FILE: leap-year period start, pre-period clamping to full legs, one-second-before-end flooring to zero, zero-length period (the divide-by-zero guard) — 3 new tests, 11 total, plus a leap-year assertion inside the existing period-start test. (5) THE SUITE STAYS HONEST: the delegating double (real adapter verify + canned fetch) is the provider; the Stripe HTTP legs stay untested live (ASSUMPTION-023), stated in the file header and the test-strategy section.
**Consequences:** The Stripe surface now has a single regression file a later refactor must keep green; a wiring break fails here first instead of surfacing as a flaky single-mechanism test. Follow-ups: none from this ticket — the open Stripe gaps (provider-side cancel, downgrade price switch, webhook supersede on `detag_upgrade_from`) belong to their owning tickets (P1-071/ASSUMPTION-034, ASSUMPTION-032).

## ADR-0038 — Razorpay adapter: reqwest + Basic auth; checkout is a subscription create; best-effort status map; single active provider; flag-off 404 (2026-11-18, Phase 1)
**Context:** E1.8/P1-073. India-market intent (ADR-0007): Razorpay is the India-native provider — UPI AutoPay, cards, netbanking, INR-first; Stripe stays the default until the owner enables the flag (owner decision #3 covers live keys for both providers; still pending). Verified against Razorpay's API docs 2026-11-18 (subscriptions create/fetch, invoices list, webhook events list, webhook signature guide).
**Decision:** (1) ADAPTER: `RazorpayAdapter` in `crates/billing/src/razorpay.rs` implements `BillingProvider` over `reqwest` 0.12 (rustls, already in the workspace) + HTTP Basic auth (`key_id:key_secret`), base `https://api.razorpay.com/v1`. No Razorpay SDK exists for Rust in the kit; the calls are plain HTTPS + JSON. Hand-written `Debug` prints nothing. (2) TEST MODE ENFORCED AT CONSTRUCTION (the P1-060 precedent): the key id must start `rzp_test_`, or `rzp_live_` with `allow_live` (owner decision #3, defaults false everywhere); the webhook secret must be non-empty; anything else is `BillingError::Configuration` naming the problem, never the key. (3) CHECKOUT IS A SUBSCRIPTION CREATE: `create_checkout` POSTs `/v1/subscriptions` with `plan_id` = `req.price_id` (the caller passes the provider-appropriate id — see 6), `total_count` = 1200 (100 years of monthly cycles, Razorpay's documented maximum; Razorpay subscriptions must be bounded, ours are indefinite), `quantity` 1, `customer_notify` true, `customer_id` when the caller has one, `notes: {detag_user_id}` (the Stripe `client_reference_id` precedent — the webhook reads it back). Returns `CheckoutSession {id: sub_..., url: short_url}` — the authorization link the buyer opens. `success_url`/`cancel_url` are unused: a Razorpay subscription carries no merchant redirect; the checkout response still returns `{id, url}`. A bad plan id (Razorpay 400 "The id provided does not exist") maps to `InvalidPrice`, like Stripe's `resource_missing`. (4) STATUS MAP, BEST-EFFORT: `active`→Active; `authenticated`→Trialing (mandate authorized, first charge made — grants like a trial); `pending`→PastDue (charge failed, Razorpay retrying); `halted`→PastDue (retries exhausted); `cancelled`/`completed`/`expired`→Canceled; `created`→`UnknownStatus` fail-closed (not authorized — do not grant); `paused`→`UnknownStatus` fail-closed (our machine has no pause; a pause must neither keep granting nor trigger dunning — the row keeps its last good state until resume/cancel). (5) WEBHOOK MAPPING (P1-074 wires the route; the mapping lands here so it is a unit test): `map_webhook` takes the subscription entity as payload (the Stripe `data.object` precedent — the handler extracts `payload.subscription.entity`). `subscription.authenticated` → `CheckoutCompleted` (user from `notes.detag_user_id`; absent → `None`, the handler logs instead of guessing); `subscription.activated` / `subscription.updated` / `subscription.resumed` / `subscription.pending` / `subscription.halted` → `SubscriptionStatusChanged` (pending/halted carry PastDue per the status map in 4, so the dunning state machine sees them); `subscription.cancelled` / `subscription.completed` / `subscription.expired` → `SubscriptionDeleted`; `subscription.charged` → `None` (the renewal's period end arrives via the subscription events; the charge itself writes no row — the P1-065 `invoice.paid` no-op precedent); `subscription.paused` → `None`; payment/invoice events → `None` (dunning runs off `subscription.pending`/`halted`, not `payment.failed` — the payment entity carries no subscription link we can trust). Unknown types → `None`. (6) PLAN LINK: `plans` gains `razorpay_plan_id TEXT` (additive migration, NULL until set — the `stripe_price_id` precedent); checkout selects the id by active provider; the webhook handler resolves plans via new `by_razorpay_plan_id` (P1-074 uses it). The admin plans editor does NOT expose it yet (follow-up; set via SQL per pricing-config — the seed leaves it NULL like `stripe_price_id`). Catalog sync stays Stripe-only (`CatalogProvider` is not implemented for Razorpay — a Razorpay plan is created in the Razorpay dashboard, its id recorded in the catalog). (7) SINGLE ACTIVE PROVIDER: `AppState` builds the Razorpay adapter when the flag is ON and Razorpay is configured; else Stripe when configured; else `None`. One provider at a time — the trait, the webhook verify, and the checkout all read the same `state.billing`. Enabling the flag makes Razorpay THE provider: a Stripe webhook then fails signature (400) and Stripe prices are not sold. Dual-provider (both webhooks live) needs a second state field — a follow-up, not this ticket. (8) FLAG-OFF 404 (the AC): `POST /v1/webhooks/razorpay` answers 404 `PF-2010` while `PF_FEATURE_RAZORPAY` is off (default) — the route exists in the spec and the route table, but the endpoint does not exist while disabled. Flag on → the 501 stub until P1-074 lands the receiver. The route-table probe expects the 404 (flag off in default settings). (9) NO PORTAL: Razorpay has no hosted customer portal — `create_portal` returns `BillingError::Provider` with a static message; the portal endpoint 500s while Razorpay is active (P1-077 parity doc lists it). Customers: `create_customer` POSTs `/v1/customers` with `name` derived from the email local part (Razorpay requires a name; the trait only carries email — sanitized to 3–50 allowed chars, fallback "Detag Customer") + `notes.detag_user_id`; `fetch_customer` GETs it. Invoices: `GET /v1/invoices?customer_id=...&count=20`, mapped to our shape (`download_url` is `None` — a Razorpay invoice has a hosted page `short_url`, no PDF file; `hosted_url` = `short_url`); the returned items are filtered client-side by `customer_id` as a backstop, because the `customer_id` query filter is not the documented one (`subscription_id` is) and an ignored filter must never leak another customer's invoices. (10) HONESTY: the HTTP legs are untested live (no Razorpay key on this VM, no network path to `api.razorpay.com` exercised — the ASSUMPTION-023 precedent). First live run is a flag-on checkout with a test-mode key.
**Consequences:** Razorpay checkout, fetch, invoices, and webhook mapping exist behind the flag; the flag-off webhook 404s; Stripe behaviour is unchanged with the flag off (default). Follow-ups: P1-074 (webhook route + idempotency), P1-075 (mock-server adapter tests), P1-076 (GST), P1-077 (parity doc), P1-078 (enable runbook), dual-provider support, admin editor for `razorpay_plan_id`, provider-side cancel (the ASSUMPTION-034 follow-up, same for both providers).

## ADR-0039 — Razorpay webhook receiver: same flow as Stripe, Razorpay envelope; body-hash event id; wrong-provider is 503 (2026-11-19, Phase 1)
**Context:** E1.8/P1-074. P1-073 built the adapter (verify + map as pure functions, ADR-0038) and left the route a flag-gated 501 stub; this ticket wires the receiver.
**Decision:** (1) RECEIVER MIRRORS STRIPE: `POST /v1/webhooks/razorpay` (flag off → 404 `PF-2010`) verifies via the real `RazorpayAdapter` (`X-Razorpay-Signature`, `hex(hmac_sha256(webhook_secret, raw_body))`, constant-time — no timestamp/tolerance, Razorpay signs the body alone), stores the envelope in `webhook_events`, maps via `map_webhook`, and dispatches through P1-065's `handle_domain_event`. Bad signature is 400 `PF-2013` (the endpoint's only 4xx); unconfigured billing is 503 `PF-5005`; every verified delivery is 200 with a receipt. (2) BODY-HASH EVENT ID: Razorpay sends no event id, so the ledger key is `sha256_hex(raw_body)` (ASSUMPTION-036) — the UNIQUE `(provider, event_id)` key is the idempotency, exactly as for Stripe; a redelivery is a replay, the stamp does not move, and still exactly one subscription row is created. (3) SHARED FLOW: the Stripe and Razorpay receivers share one `store_and_dispatch` (ledger insert, replay no-op, undispatched re-dispatch per P1-065) — the P1-063 behaviour is unchanged; only the envelope parse (`event` + `payload.subscription.entity`, not `id`/`type`/`data.object`) and the signature step differ. (4) WRONG-PROVIDER IS 503: the receiver only runs when Razorpay is the active provider; with Stripe configured instead it answers 503, not a misleading 400. (5) PLAN LOOKUP TRIES BOTH IDS: the webhook handler resolves the checkout's plan from `fetch_subscription`'s `price_ids`, trying `by_stripe_price_id` then `by_razorpay_plan_id` — the Razorpay adapter reports the Razorpay plan id there (P1-073). (6) HONESTY: the Razorpay HTTP legs stay untested live (ASSUMPTION-035) — the suite proves the receiver through the real HTTP layer with the real adapter + a delegating `fetch_subscription` double; no test calls Razorpay.
**Consequences:** The Razorpay webhook is live behind the flag: tamper is 400, replays are no-ops, `subscription.authenticated` creates the row with the plan resolved from `razorpay_plan_id`, terminal events cancel through the state machine. Follow-ups: P1-075 (mock-server adapter tests), P1-077 (parity doc — portal still 500s under Razorpay, ADR-0038 §9).

## ADR-0043 — Completion true-up: estimate at create, real seconds at completion, on the create day (2026-11-19, Phase 1)
**Context:** P1-079. P1-050 built the meter (`record` the estimate at create, `reconcile_day` for drift) but left the second half of the spec open: the estimate is a reservation, and the real duration is only known when the job finishes. Until this ticket, an over-estimate could never be corrected — `record` clamps negative deltas to 0 and `usage_counters::increment` requires ≥ 0 (plus the table CHECK) — so a video that ran shorter than estimated would over-charge the user for the whole day.
**Decision:** (1) PURE MATH, TESTED ALONE: `true_up_delta(estimated, actual) = actual - estimated`, saturating, negative inputs clamped to 0 — the ticket's AC, proven by 3 unit tests (over/under/exact, unknown-at-create, clamps, saturation). (2) `UsageMeter::true_up(user_id, day, estimated, actual)` applies the delta to both stores and returns the outcome (`delta_applied`, the new DB total, the new Redis total). The day is an explicit argument — the job's CREATE day (ASSUMPTION-040) — never the clock's today. (3) DB-FIRST ORDER: the DB decides the applied delta (floored at 0 via `usage_counters::adjust`, which clamps in SQL on both legs — the `EXCLUDED` trap, where the clamped insert row would have zeroed a negative delta on the conflict leg, is fixed by using the raw `$3`/`$4` parameters in the `ON CONFLICT` SET clause, proven by the refund tests failing before the fix and passing after); Redis receives exactly the applied delta, additionally clamped against the hash's own value so it never goes negative. (4) NO WIRING YET: no production caller exists — job creation is the 501 stub and completion lands in Phase 2 — so this ticket ships the mechanism + 4 live tests, and Phase 2 wires `record` at create and `true_up` at completion. (5) NO NEW ROUTE, NO MIGRATION, NO CONFIG: the `usage_counters` table already exists; the per-key attribution still reads 0 (jobs carry no duration) until Phase 2 records.
**Consequences:** A finished job's charge is exact in both stores; a refund can never drive a counter negative; the create-day rule keeps a midnight-crossing job's accounting on the day it was reserved. The next reader that wires completion must pass the job's create day, not today.

## ADR-0044 — Usage read: the billing exception to "no billing for keys" (2026-11-19, Phase 1)
**Context:** P1-080. The standing rule is "no billing for keys": checkout (P1-062), portal (P1-067) and invoices (P1-068) are JWT-only and any API key is 403 `PF-1002`, because those routes move money or expose provider state. `GET /v1/usage` moves nothing and exposes only the caller's own metering — the same data `jobs:read` already gates on the jobs nest — so the ticket spec ("per-key breakdown when api key used") asks for the one billing read a key may make.
**Decision:** (1) THE USAGE READ IS THE BILLING EXCEPTION: a key carrying `jobs:read` reads its key owner's usage (the extractor's scope table gains the row; the matrix row flips `Unprotected` → `Allowed("jobs:read")`). Money-moving billing routes stay closed to keys — this ADR opens one read, not billing. (2) JWT CALLERS GET BUCKETS ONLY: a JWT caller gets `today` + the 30 daily buckets and no `by_key` field at all (the field is absent, not empty). (3) KEY CALLERS GET THE FULL PER-USER BREAKDOWN FOR TODAY: every key that created a job today plus the unattributed row for web / JWT-created jobs — the breakdown is the user's, and the calling key was minted by the owner it reports on; key prefixes are labels, not secrets (they already ride the admin jobs list). (4) THE DB IS THE SOURCE OF TRUTH: buckets read the durable `usage_counters` rows (`for_user_range`, one query for the whole window), never the Redis hot hash, which may drift until the nightly reconciliation (P1-082). (5) ZEROS, NOT 404: a user who used nothing gets today zeros + 30 zero buckets (+ an empty `by_key` for a key caller) — a list endpoint answers "what do I have?", and "none" is a valid answer. No audit row, no idempotency — a read creates nothing durable. (6) THE PER-KEY `video_seconds` IS 0 UNTIL PHASE 2: jobs carry no duration, so the only honest per-key video number today is the video-job count in `video_jobs`; the buckets' `video_seconds` are real (they read the counters P1-079's true-up maintains).
**Consequences:** The matrix counts move to 14 Allowed / 33 Forbidden / 9 Unprotected / 11 Ignored. The next billing read that wants key access must justify its own exception the same way — this ADR does not open billing to keys generally, and any route that moves money or touches a provider stays JWT-only.

## ADR-0045 — Admin usage view: the admin sees everything, the CSV is window-only (2026-11-19, Phase 1)
**Context:** P1-081. The admin view is the P1-080 usage read for an arbitrary user, for billing disputes: support needs to answer "how much has this user used?" without asking the user to export anything. The two questions the spec ("Per-user 30d + totals; CSV export endpoint (admin) for billing disputes") leaves open are what the admin sees that the user does not, and what the CSV carries.
**Decision:** (1) THE ADMIN SEES EVERYTHING: the JSON view is the P1-080 shape (today + the 30 buckets ending today) plus the all-time `totals` (the SUM over every `usage_counters` row, not just the window — a row 40 days back counts in the totals but not in the window) plus `by_key` ALWAYS present (calling key, sibling keys, and the unattributed row) — the P1-080 rule that a JWT caller gets no `by_key` at all does not apply to an admin, who is entitled to the whole picture (ADR-0044's "prefixes are labels, not secrets" applies a fortiori). (2) THE CSV IS THE WINDOW ONLY: one header row (`date,images,video_seconds`) plus one row per day, oldest first, trailing newline — no totals row, because a dispute tool sums the rows itself and a totals row would break a parser that expects every row to be a date; the totals live in the JSON view. The values are a date and two integers by construction, so no field ever needs quoting or escaping. (3) UNKNOWN USER IS 404, UNUSED USER IS ZEROS: the admin asked about a specific user, so a missing id is a wrong id (404 `PF-2010`, the P1-008 precedent for admin lookups); a user who exists but used nothing gets zeros in JSON and the header plus 30 zero rows in CSV (the P1-080 precedent — a list endpoint answers "what do they have?"). (4) ADMIN + SUPPORT, NO KEYS EVER: the routes sit behind `AdminReadContext` (`admin.usage.read`) — support reads, plain users and any API key are 403 `PF-1002` ("no admin ever", P1-043), anonymous is 401. No audit row (P1-046 — a read creates nothing durable), no Redis read (the DB is the source of truth, P1-082's nightly reconciles the hash, it never feeds an answer).
**Consequences:** The matrix gains two `Forbidden` rows (counts now 14 Allowed / 35 Forbidden / 9 Unprotected / 11 Ignored); the route table moves 69 → 71 routes, the OpenAPI handlers 35 → 37. The next admin read that wants a totals row in its export must justify breaking the one-row-per-day contract.

## ADR-0046 — Nightly reconciliation: DB wins, window today + yesterday, audit beyond 10 images / 60 video-seconds (2026-11-19, Phase 1)
**Context:** P1-082. P1-050 built the meter (Redis hash first, DB row second) and the `reconcile_day` CAS mechanism, but left the nightly job itself open: nothing ever ran the repair, so drift from a failed DB write (or a crashed process between the two legs) sat in Redis until the 48 h TTL expired it — and the quota pre-check reads the DB, so the drift was invisible to enforcement but visible to any reader of the hash. The ticket spec ("Nightly: redis vs db drift, db wins, anomaly report; audit on corrections beyond threshold") names the job but not the window, the thresholds, the candidate set, or the schedule.
**Decision:** (1) THE WINDOW IS TODAY + YESTERDAY: the hash TTL is 48 h, so yesterday is the oldest day whose hash can still exist; reconciling older days would resurrect expired hashes. Today is reconciled in progress — the CAS makes that safe, and tomorrow's run catches later drift. (2) THE CANDIDATE SET IS DB ROWS UNION REDIS KEYS: `usage_counters::user_days_since` (one new read query) plus a SCAN of `pf:usage:*:{day}` per window day, parsed back to (user, day) — the SCAN is the only leg that sees a Redis-only hash, the `record` failure mode. (3) DB WINS, INHERITED: `reconcile_day` (P1-050) is the mechanism, unchanged — a missing DB row reads as zeros, so a Redis-only hash is zeroed. That is the settled semantics, not a new decision: the DB is the source of truth and a row the DB never got is not usage the quota decisions can see (ASSUMPTION-043). (4) THE ANOMALY THRESHOLDS ARE 10 IMAGES / 60 VIDEO-SECONDS (config, defaults 10 / 60; 0 audits every correction): a correction is an anomaly when either leg's drift magnitude reaches its threshold, in either direction. Sub-threshold corrections are corrected silently; anomalies write one `billing.usage.reconciled` audit row each (actor none, client `reconciliation`, before/after pairs) — the audit rows ARE the durable anomaly report. (5) THE SCHEDULE IS WALL-CLOCK, 02:00 UTC (config `PF_WORKER_NIGHTLY_HOUR_UTC`, default 2): the worker's `nightly` task sleeps until the next run, enqueues the `reconciliation` kind on the `reconciliation` queue, and repeats until shutdown. An enqueue failure logs and waits for the next night — the job is idempotent, so a missed night is repaired the night after. (6) THE SCHEDULE ENQUEUES RECONCILIATION ONLY: `dunning` and `catalog_sync` stay unenqueued until their handlers land — enqueueing a job a stub would log-and-ack is a dropped job, not a nightly run (ASSUMPTION-043). (7) THE HANDLER IS REAL WHEN THE CONTEXT CARRIES SERVICES: `WorkerContext.services` (`WorkerServices`: pool + Redis pool + clock + `ReconcileConfig`) is built once in `main.rs` and shared by every replica; without services the handler stays the Phase-0 stub (unit-test contexts). A job error (listing failure) propagates so apalis retries; a per-day failure is counted inside the report and never fails the job. (8) HONESTY: no production caller records usage yet — job creation is the 501 stub and completion lands in Phase 2 — so the tests seed `usage_counters` rows and corrupt Redis hashes directly; the per-key `video_seconds` still reads 0 until Phase 2 records durations.
**Consequences:** Drift is now repaired nightly with an audit trail for real anomalies; the worker gains a wall-clock scheduler and a services context its future real handlers (dunning, catalog sync) will reuse. ## ADR-0047 — Abuse spike detection: velocity rule files a report + audit; auto-suspend OFF by default (2026-11-19, Phase 1)
**Context:** P1-083. The ticket spec ("Velocity rules (N jobs/minute threshold) create abuse_reports entries + alert; auto-suspend flag OFF default") names the trigger and the two outcomes but not the threshold, the window, what "alert" means, how a sustained spike avoids filing once per job, or what auto-suspend does when it is on. The `abuse_reports` table (migration 004) has no `user_id` — a system-raised report could not say WHO spiked — and there is no production caller yet: job creation is the 501 stub until Phase 2.
**Decision:** (1) THE RULE IS A COUNT, NOT A RATE LIMIT: `detag_core::abuse::check_velocity` counts the user's `jobs` rows created inside the trailing window (`jobs::count_created_since`, every status — a spammer's jobs fail fast and failed jobs must still trip the rule) and trips when the count reaches the threshold (inclusive). No Redis leg: the `jobs` table is the source of truth for creations. (2) THE DEFAULTS ARE 30 JOBS / 60 SECONDS (config `PF_ABUSE_SPIKE_JOBS_PER_MINUTE` / `PF_ABUSE_SPIKE_WINDOW_SECONDS`, validated `>= 1` at boot): no legitimate interactive burst reaches 30 creations in 60 s — but a Business batch legitimately can, and that trip is the expected signal (a report for a human to clear), not a false positive to tune away. (3) A SPIKE FILES ONE REPORT + ONE AUDIT ROW: the report (`abuse_reports`, status `open`, reason `velocity: N jobs in 60s (threshold M)`, `user_id` set — new nullable column, P1-083 migration, so the public intake keeps leaving it NULL) and the audit row (`abuse.spike_detected`, actor none, client `abuse-spike`, before/after pairs) ARE the alert — the mailer precedent (`email.rate_limit_tripped`): no separate alert channel, no email. (4) A SUSTAINED SPIKE FILES ONCE PER WINDOW: the detector checks for an open report for the user inside the window before filing, and re-checks inside the filing transaction — a second check returns the existing report id with `already_reported: true` and writes nothing. A report an admin already moved to reviewing/resolved does NOT dedup: it is a handled report, and a fresh spike deserves a fresh row. (5) AUTO-SUSPEND IS OFF BY DEFAULT (`PF_ABUSE_AUTO_SUSPEND`, default `false` — the ticket's second AC): with it off, a spike is reported + audited and nothing else happens — the user keeps their account, sessions, and jobs. With it on, the spike also suspends the account through the FULL P1-008 sequence (status flip + every live session revoked + every queued job held, audited as `user.suspended` with the velocity reason, actor none, client `abuse-spike`) in the same transaction as the report; an already-suspended account is left alone (the spike is still reported, but a second suspend would be a second audit row for a no-op). Suspending the whole account for a velocity trip is deliberately heavy — that is why the flag defaults off and the owner turns it on deliberately, never by accident. (6) THE KILL-SWITCH IS `PF_ABUSE_SPIKE_ENABLED` (default true): `false` means the check runs but files nothing (`checked: false`), the dunning/reconciliation precedent. (7) NO WIRING YET (ASSUMPTION-044): no production caller exists — job creation is the 501 stub and completion lands in Phase 2 — so this ticket ships the mechanism + 7 live tests, and Phase 2's job-create calls `check_velocity` after each insert. The check is cheap (one COUNT + one indexed dedup scan) and safe to call per insert.
**Consequences:** Spikes are now detectable with a human-reviewable trail and an opt-in enforcement switch that defaults to report-only; the admin abuse queue can list system reports per user (the new `user_id` + index). Follow-ups: the Phase 2 job-create wiring (ASSUMPTION-044), and the admin abuse-reports read/resolve routes are still stubs — the queue rows exist, the endpoints that serve them do not (a follow-up, not this ticket).

## ADR-0048 — Metering suite: the convergence property, not the atomicity property (2026-11-20, Phase 1)
**Context:** P1-084. The ticket spec names four legs — races (parallel creates under limit), midnight rollover (clock), true-up math, drift reconciliation — with the single AC "suite green". The four behaviours already existed (P1-050 / P1-079 / P1-082); what did not exist was one suite proving them under the conditions that break counters, and one honest statement of what the race leg can and cannot prove. The suite's race test found a real property gap while it was being written: the first version asserted Redis == DB == 20 immediately after 20 concurrent records raced 30 reconciles, and Redis read 12.
**Decision:** (1) THE RACE LEG PROVES CONVERGENCE, NOT ATOMICITY: a record's Redis increment can land between a reconcile's DB read and its CAS, and the CAS then sets the hash back to the DB value it read — transiently wiping that increment from Redis. The DB upsert still lands (the durable row is never wiped — the DB read 20/20 in the failing run), and the next reconcile repairs the hash. So the suite asserts: DB == 20 exactly after the join, one reconcile after the settle makes Redis == 20, and a second reconcile is a no-op. The P1-050 module doc and the `reconcile_day` doc said "a concurrent record is never wiped" — that sentence overclaimed for the Redis leg and is corrected in this commit to the convergence statement. (2) THE QUOTA DECISIONS NEVER SEE THE LAG: the pre-check (P1-051) and `/v1/me` read the durable snapshot, never the hash, so a transiently-behind hash is never an enforcement error — the lag is a metering-mirror lag, repaired by the next reconcile. (3) THE ATOMIC CHECK-AND-RECORD RACE IS OUT OF SCOPE FOR THIS SUITE: the check is read-only today (P1-051) and the atomic check-and-record lands with real job creation in Phase 2 — so no test here proves a check immediately followed by a record under a limit at the HTTP layer. The suite proves the meter-level properties that check-and-record will rely on (exact totals under concurrency, the snapshot reading exactly what the meter recorded, reconcile converging after the settle). The HTTP-level limit trip itself is already proven in `entitlements.rs` (P1-057: Free 9/10 reaches the stub, 10/10 is 429 `PF-3001`). (4) THE SUITE IS ONE FILE, `crates/core/tests/metering_suite.rs`, 8 live tests, April-2027 frozen dates spaced 3 days apart (no other suite freezes April 2027, so the SCAN-based job test cannot overlap another suite's window): under-limit parallel records (8 < Free's 10/day, limit read from the seeded catalog); records racing reconcile (the convergence proof above); rollover splitting images + video-seconds across days; a record at exactly 00:00:00 landing on the new day; true-up math exact across five mixed jobs (final video-seconds == sum of actuals, 285); interleaved refunds flooring at 0 with a retried completion a no-op; reconcile repairing both legs at once; the nightly job repairing yesterday's drift after a midnight crossing, audited on the video leg (Δ60 reaches the threshold). No new product code, no new route, no migration, no config (ASSUMPTION-045).
**Consequences:** The metering behaviours now have one suite that names the exact property each leg proves, and the reconcile doc no longer overclaims. Follow-ups: the Phase 2 atomic check-and-record race test (with real job creation), and the Phase 2 wiring that makes the suite's "no production caller records usage yet" honesty note stale.

## ADR-0049 — Quota warning emails: thresholds in config, the cap in the outbox index (2026-11-20, Phase 1)
**Context:** P1-085. The ticket spec ("80%/100% thresholds (config) warning emails with once/day cap; outbox tests cover", AC "capped correctly") names the thresholds, the cap, and the proof surface — but not what "cap" means under concurrency, where the check lives, which dimension trips when both are near their limits, what a 0 limit means, or whether a warning writes an audit row. There is no production caller yet: usage is recorded only by tests (job creation is the 501 stub, completion lands in Phase 2).
**Decision:** (1) THE DECISION READS THE DURABLE SNAPSHOT: `maybe_warn_quota` takes the user's effective plan (resolved once by the caller — the quota gate's `effective_plan`) and the UTC day, and reads `quota_snapshot_for_plan` — the DB row, never the Redis hash — so the warning agrees with the quota gate by construction; the same two sources as `/v1/me`. (2) THE LEVEL IS THE HIGHEST PERCENT ACROSS DIMENSIONS WITH A LIMIT: each dimension's percent is `used * 100 / limit` (i128 math); the tripping dimension is the highest percent, ties go to images (deterministic). A dimension with limit 0 is skipped — Free's 0 video-seconds limit is "not granted", not a percent (and not infinite percent once any video-second is used). Level is `Full` at or above `full_pct`, `Warn` at or above `warn_pct`; a jump straight past the warn threshold sends only the full mail. (3) THE CAP IS A PARTIAL UNIQUE INDEX, NOT A SECOND TABLE: `email_outbox_quota_warn_once_idx` on (`template`, `payload->>'user_id'`, `payload->>'day'`) for the two warning templates only (migrations 20261120021325 + 20261120023438, index-only — the table count stays 24). `try_enqueue_quota_warning` inserts with `ON CONFLICT DO NOTHING`, so the insert IS the cap check: two concurrent calls racing the same threshold land exactly one row, with no advisory lock and no read-then-write race. The template IS part of the key: the first version keyed on (user, day) only, so an 80% mail sent blocked the same day's 100% mail — the ticket's own live test (`full_at_100_enqueues_100_template`) caught it before the commit, and the fix migration put the template in the key. The two levels are independent caps (an 80% mail sent does not block the 100% mail later the same day), and the cap resets with the counters at the UTC boundary (the `day` key changes). A sent row still counts — the cap is one mail per day, not one unsent row per day. The payload MUST carry `user_id` + `day` (the index reads exactly those two keys; a payload missing either would silently escape the cap). (4) THE THRESHOLDS ARE CONFIG, 80/100 BY DEFAULT: `PF_BILLING_QUOTA_WARN_ENABLED` (kill-switch, default true), `PF_BILLING_QUOTA_WARN_PCT` (80), `PF_BILLING_QUOTA_WARN_FULL_PCT` (100), validated 1..=100 with warn < full at boot — equal thresholds would make the two levels indistinguishable. (5) NO AUDIT ROW: a warning is a routine notification, not an anomaly — the outbox row itself is the record (support reads it per user + template, the resend-limit precedent). The dunning reminders differ: they are part of a money-owed sequence, so they audit. The drain treats both templates as Transactional (never capped by the per-recipient hourly caps) — a quota warning must reach the user precisely when the quota is gone. (6) NO WIRING YET (ASSUMPTION-046): the Phase 2 intake calls `maybe_warn_quota` after each successful `record` and after each `true_up` (a true-up can also push a day over a threshold); the function takes the day explicitly so the caller owns it, exactly like `true_up`. The templates state only the tripped dimension's numbers plus the `/billing` and `/plans` links (the plan-matrix link precedent) and make no product claims; their bytes are pinned by the mailer snapshots.
**Consequences:** Users now get a warning before the quota gate starts rejecting them, and the cap holds under concurrency by construction (the index), not by convention (a check-then-insert). Follow-ups: the Phase 2 intake wiring (ASSUMPTION-046); whether support wants a warning-history view (the outbox already answers it per user + template).

## ADR-0050 — Metering design consolidated: counter semantics, clock-skew and retry rules decided (2026-11-20, Phase 1)
**Context:** P1-086. P1-050 / P1-079 / P1-080 / P1-081 / P1-082 / P1-084 / P1-085 each built one metering piece and recorded its own ADR and assumption, but no single doc said how the pieces fit, what the edge cases do, or which claims were still overclaiming. The consolidated design doc is `docs/06-DELIVERY/13-metering-design.md` (ASSUMPTION-047). This ticket also corrects three overclaims found while consolidating (see the design doc §6 for the full list).
**Decision:** (1) THE DESIGN DOC IS THE CONSOLIDATED STATEMENT: counter semantics (two counters per user per UTC day, Redis hot mirror + Postgres durable truth, DB wins), the reader table (every decision reads the durable snapshot or the DB rows — the Redis hash is never a decision source), the reconciliation policy (window today + yesterday, DB rows UNION Redis SCAN, DB wins, thresholds 10 / 60, one `billing.usage.reconciled` audit row per anomaly, 02:00 UTC, reconciliation only), and the warning rules (snapshot source, highest-percent trip, index cap) live in the design doc; the per-ticket ADRs stay the decision record and are cited, not rewritten. (2) CLOCK SKEW: the meter trusts the host system clock (`SystemClock` = `Utc::now()`; the nightly loop reads `Utc::now()` directly — the same host clock in production). No skew detection and no NTP discipline in code; time sync is an ops concern. A forward jump under-counts today (quota resets early); a backward jump can push a settled day over its limit after the gate ran (accounting only); skew is invisible to reconciliation (both legs were written with the same clock, so they agree — the error is a wrong-day row, not drift); a skipped or double-fired night is harmless (the job is idempotent). The ±5 min skew tests and handling are P5-043's follow-up. (3) RETRY: neither `record` nor `true_up` is idempotent — a duplicate `record` adds twice, and a retried `true_up` re-applies its delta. The floor bounds a retried refund at 0 but does not make it a no-op (proven by a scratch probe in this ticket: a retried 90→0 true-up against a day total of 10 applied −10 and stole the other job's reservation — the P1-084 "retried completion is a no-op" claim is corrected to the floor bound). The real guard is completion-processed-once at the caller: Phase 2 must check the job's terminal state before calling `true_up`, and the intake must call `record` once per job. The retry guards that do exist are the warning cap (idempotent by construction — the partial unique index) and reconciliation (idempotent — a second run is a no-op). (4) RETENTION IS UNENFORCED: the data-model's "usage_counters: keep 400 d" is a stated policy with no purge mode behind it (`detag-gc` has only `--purge-users` and `--purge-sessions`); rows accumulate for live users and the admin totals SUM over all of them. A `detag-gc --purge-usage-counters` mode is the follow-up, not this ticket. (5) NO WIRING YET: still no production caller records or trues up — job creation is the 501 stub and completion lands in Phase 2 — so the Phase 2 wiring list (record at create, true_up at completion on the create day, `maybe_warn_quota` after each, `check_velocity` after each insert) is recorded in the design doc, not claimed as done.
**Consequences:** The next reader wires Phase 2 from one doc instead of seven ADRs, and the three corrected claims can no longer be re-read as promises. Follow-ups: P5-043 (clock skew), the usage-counters purge mode, the Phase 2 atomic check-and-record + its race test and the completion-processed-once guard.

## ADR-0051 — Audit service is the only write path to the audit trail (2026-11-20, Phase 1)
**Context:** P1-087. `audit_logs` existed since migration 004 (P0-040) and 40 call sites across 22 files wrote to it directly through the repository, with no validation and no single place stating the write contract; `crates/core/src/audit.rs` was a placeholder ("implemented by its epic ticket"). FR-C-03 requires every privileged and provenance-related action to append to an append-only audit log, and the ticket's AC is "append-only enforced".
**Decision:** (1) THE SERVICE OWNS WRITES: `detag_core::audit::record` is the single entry point — it validates the event, then inserts through the repository, taking `impl Executor` so the same call works against the pool and inside a transaction. All 40 direct call sites (16 api services, `audit_middleware`, `rate_limit`, mailer drain, `detag-gc` purge, `abuse`, `reconciliation`) now call it; `NewAuditLog`/`AuditLog` are re-exported from the service so callers have one import. (2) ENFORCEMENT IS COMPILER + TEST: the repository `insert` is `pub(crate)` — no other crate can write a row, the compiler rejects it — and a unit test in the service scans the workspace source for `audit_logs::insert` outside `audit.rs`, so a direct call inside `detag_core` fails `cargo test`. Reads (`list_for_target`, `list_for_action`) stay public for the P1-088 query API and the tests. (3) VALIDATION IS SHAPE ONLY: action non-empty, dotted, no whitespace; target type non-empty, no whitespace; failure is `RepoError::InvalidInput` (new variant) and writes nothing. Payload privacy (NFR-42) stays the caller's job — the service cannot detect PII in arbitrary JSON. (4) APPEND-ONLY IS THE TRIGGER, NOT A GRANT: UPDATE/DELETE raise on `audit_logs_append_only` (migration 004, reaffirmed by P1-007); a GRANT cannot work because the dev role owns the tables. The live test proves UPDATE/DELETE denied on a service-written row against the current schema. (5) NO SCHEMA CHANGE: no new table, route, migration or config.
**Consequences:** A future writer that bypasses the service fails the build (other crates) or the test suite (this crate); a malformed event fails loudly instead of landing a bad row. P1-088 builds its query API on the service's read side. Follow-up: P1-092's matrix suite proves every privileged action is actually audited (shape validation cannot catch a well-formed but wrong action).

## ADR-0052 — Audit query API: newest-first keyset read over the existing indexes, no new index (2026-11-20, Phase 1)
**Context:** P1-088. The ticket spec ("GET /v1/admin/audit?actor=&action=&target=&from=&to= cursor-paginated; indexes per data-model", AC "filters + pagination tested") names the endpoint, the filters, and the pagination — but not the order, the window semantics, what `target` means, whether an unknown filter 404s, or whether a new index is needed. The `AdminAuditRead` capability and the matrix row already exist (P1-042/043); the route was the guarded `admin_read_stub` (501).
**Decision:** (1) NEWEST FIRST: the list orders by `(created_at, id)` DESC — an audit viewer reads the most recent events first (the list_jobs "browse, newest first" precedent; the users search orders oldest-first because a directory reads forward). The keyset is the same `(created_at, id)` pair, compared on `date_trunc('milliseconds', created_at)` so the cursor's Unix-millis ts matches the repo comparison exactly. (2) FILTERS ARE EXACT AND ANDed: `actor` is the acting user's id (UUID), `action` the exact dotted name, `target` the target's id (any target type — the console links "events for this user/job" by id, and the type rides on every row; a `type:id` composite would be undiscoverable), `from`/`to` the half-open window `[from, to)` (a row exactly at `to` belongs to the next window; an inverted window is an empty page, not an error — the SQL yields nothing). An unknown actor id is an empty page, not a 404 (the P1-080 precedent: a list never 404s on its filter). (3) NO NEW INDEX: the data-model indexes are the two that exist — `audit_logs_actor_created_idx` (`actor_user_id, created_at DESC`, which serves the actor filter + the ordering) and `audit_logs_target_idx` (`target_type, target_id`, which serves the target filter, the result then sorted). The action and `from`/`to` filters have no dedicated index: they filter the rows the ordering scans. The ticket's "indexes per data-model" is satisfied by the existing two, and adding a `(created_at DESC, id DESC)` index the data model does not name would be scope creep with no measured need — the viewer is a low-frequency admin endpoint and the table is small in Phase 1. If the trail grows past comfortable seq-scan + sort, the follow-up is that index, measured first with EXPLAIN on the unfiltered list. (4) NO AUDIT ROW FOR THE READ: the endpoint writes nothing (P1-046 — reads are not audited); the handler does not mark `AuditHandled` and the middleware stands down on reads anyway. The endpoint does not redact: `before`/`after` round-trip verbatim, and NFR-42 stays the writers' contract (hashes, never raw PII). (5) NO SCHEMA CHANGE: no new table, migration, config, or route (the route already exists in the table) — the handler replaces the stub, the OpenAPI handlers move 37 → 38 and the stubs 34 → 33.
**Consequences:** The admin console gets a real audit viewer with the same pagination contract as the other admin lists; the liveness markers the suite pins (guard walk, authz matrix, support-readonly stub list, API-key matrix note) move in the same commit. Follow-up: the `(created_at DESC, id DESC)` index if the unfiltered list ever measures slow; P1-092's matrix suite (the shape-only honesty from ADR-0051 still stands).

## ADR-0053 — Abuse intake: honeypot first, per-IP bucket, unknown job 404, one transaction with ack (2026-11-20, Phase 1)
**Context:** P1-089. The ticket spec ("POST /v1/abuse (public, rate-limited, honeypot field): job id/reporter contact/reason creates row; ack email template", AC "honeypot drops bots") names the endpoint, the honeypot, and the ack — but not the check order, the bucket key, what a filled honeypot answers, whether a named job must exist, or what the ack carries. The intake is public (no account, no credential) and writes the P1-083 `abuse_reports` table (the P1-083 detector is the other writer); the admin queue read/resolve routes are still stubs (P1-090).
**Decision:** (1) HONEYPOT FIRST: the `website` field (a hidden field a human never sees) is checked before rate limiting and before any DB work. Any non-blank value drops the submission — no row, no audit, no mail, no bucket token — and still answers the same 201 shape `{id, status: "open", created_at}` with a random `Uuid::now_v7()` id and the current time, so a bot cannot tell a drop from a filing. A filled honeypot is never a 422 (a 422 would teach the bot what tripped it). (2) PER-IP BUCKET: the rate limit is a new `abuse-intake` scope (burst / refill from `PF_RATE_LIMIT_ABUSE_INTAKE_BURST` / `PF_RATE_LIMIT_ABUSE_INTAKE_REFILL_PER_MIN`, default 5/5, validated `>= 1` at boot), keyed by the sha256 of the client IP — the reporter has no account, so the login-IP precedent applies. A trip is 429 `PF-3007` with `Retry-After` + the bucket's `X-RateLimit-*` trio; Redis down fails open (P0-103); `"unknown"` IP skips the bucket (the login precedent). (3) UNKNOWN JOB 404s: a named `job_id` that does not exist is 404 `PF-2010` (the P1-008 / P1-081 precedent for "named id does not exist"). The check is a read, not a lock, before the transaction — the `abuse_reports.job_id` FK would reject the insert anyway, and a 500 for a wrong id would be a lie. The FK is the backstop, not the check; a concurrent delete turns into `ON DELETE SET NULL`, so the report still files and survives with `job_id` NULL. Job ids are unguessable UUIDs, so the 404 reveals nothing to a caller who does not already hold the id. (4) ONE TRANSACTION: the filing writes the `abuse_reports` row (`user_id` NULL, `job_id` optional — absent means a general-abuse report — contact as filed, `status` `open`), one `abuse.report_filed` audit row (actor none, client `abuse-intake`, `after` carrying `{job_id, email_hash}` — never the raw address), and one `abuse-report-ack` outbox row (to_hash the contact's sha256, payload `{report_id}` only). The contact is normalized (trim + lowercase) and `validate_email`-checked; the reason is 1–500 chars via the existing `validate_reason` (the P1-008 shape). (5) ACK VIA THE DRAIN: the `abuse-report-ack` template (subject/text/html, Transactional class, uncapped) states the 72 h review target and makes no product claims. The drain's `resolve_recipient` special-cases it — it loads the report by `payload.report_id` and verifies the hash — because the outbox payload carries no `user_id` and the ack would otherwise park permanent ("payload has no user_id"), the P1-085 honesty precedent. (6) NO NEW TABLE, MIGRATION, OR INDEX: the intake writes the P1-083 table; the OpenAPI handlers move 38 → 39 and the stubs 33 → 32; the API-key matrix row `POST /v1/abuse` moves `Unprotected` → `Ignored` (anonymous and keyed responses identical), counts 14 Allowed / 35 Forbidden / 8 Unprotected / 12 Ignored.
**Consequences:** A reporter gets a ticket id and an ack mail; a bot gets the same 201 shape for a filing it never made; a filing about a deleted job survives as a general report. Honesty: the intake files reports into a queue nobody can read yet (P1-090), and a honeypot drop is indistinguishable only from the outside — the drop is visible in no log and no counter, so a surge of bots is silent until the queue lands; the 72 h target is a stated aim, not an SLA — FR-C-06's SLA tracking lands with the queue.

## ADR-0054 — Abuse queue: four resolve actions, SLA pair on the item, two audit rows for a suspension (2026-11-21, Phase 1)
**Context:** P1-090. The ticket spec ("Admin queue (open/reviewing/resolved) with actions: reject job, suspend user, dismiss — all audited; SLA timestamps (72h target)", AC "actions audited") names the three states and the three terminal actions — but not how a report ever becomes `reviewing`, what the SLA timestamps are, what a rejection does to the job, what audit rows the actions write, or what happens on a second resolve. The intake (P1-089) files rows nobody could read; the resolve route's audit action was already promised as `admin.abuse_reports.resolved` (authz.rs + the admin guide).
**Decision:** (1) FOUR ACTIONS, not three: the resolve endpoint takes `start_review` in addition to the spec's three terminal actions. The spec names the three queue states but only terminal actions — without a pickup transition no report could ever become `reviewing`, so the middle state would be dead. `start_review` moves open → reviewing and audits as `abuse.report_reviewing` (it resolves nothing, so the resolved action name would be a lie). (2) TERMINAL ACTIONS: `reject_job` sets the reported job's status to `rejected` (`jobs.status` is plain TEXT with no CHECK — `rejected` is a terminal value the Phase 2/3 lifecycle never writes back out of) and resolves the report as `job_rejected`; `suspend_user` runs the full P1-008 sequence on the reported user (status `suspended`, sessions revoked, queued jobs held, a pending deletion cancelled by the status flip) and resolves as `user_suspended`; `dismiss` resolves as `dismissed` with no other effect. A report that cannot take an action is 422 `PF-2002` (`reject_job` needs a `job_id`, `suspend_user` needs a `user_id` — a general-abuse report has neither, a spike report has a user but no job). (3) AUDITS: every action is audited in the same transaction as the mutation (the P1-008 atomicity), and the handler marks `AuditHandled` so the P1-046 middleware stands down. The three terminal actions write `admin.abuse_reports.resolved` (actor the admin, `after.action` naming the action — the name the matrix already promised); a suspension additionally writes `user.suspended` (the P1-008 shape — the suspension is a privileged action of its own, and the P1-092 matrix suite checks it by that name; a suspension visible only inside the resolution row would be invisible to the `user.suspended` filter). The pickup writes `abuse.report_reviewing`. (4) IDEMPOTENCY: resolving an already-resolved report is a 200 with the report as it stands — no write, no audit (the P1-071 precedent); picking up an already-reviewing report is the same. A concurrent resolve is decided by the conditional UPDATE (`WHERE status IN ('open', 'reviewing')`) — the loser re-reads and answers the no-op. The resolve runs FIRST inside the transaction, before the action's effect (the 128th's adoption-review fix): the first version flipped the job / suspended the user first and resolved second, so a loser committed that effect under a report resolved (by the winner) as something else, with no resolution audit row naming it. A loser now writes nothing at all. The race itself is code-reviewed, not test-proven (the P1-083 precedent — forcing it needs two concurrent resolves racing the filing transaction, a flaky-prone test, not written). (5) SLA: the item carries `sla_due_at` (`created_at` + 72 h, computed — no column) and `sla_breached` (a resolved report: its `resolved_at` is past the due time; an open or reviewing one: the clock is past it). The 72 h is a target, not a contractual SLA. (6) NEW COLUMNS: `resolved_at` + `resolved_by` (migration `20261121001300`, `resolved_by` REFERENCES `users (id) ON DELETE SET NULL`) — stamped exactly on a resolve, because `updated_at` cannot tell a late resolution from an on-time one (moving open → reviewing bumps it too). ## ADR-0055 — Enforcement ladder: warn → suspend → terminate, one endpoint per rung, termination is sticky (2026-11-21, Phase 1)
**Context:** P1-091. The ticket spec ("Warning to suspension to termination ladder helpers + template emails; suspension effects (sessions killed, jobs held) tested", AC "ladder e2e green") names the ladder (FR-C-02: "violation leads to warning → suspension → termination") but not the shape: whether the ladder is one endpoint or three, where the ladder state lives, what a termination is in a system whose only terminal-ish status is `deletion_pending`, or what stops a terminated user from logging back in.
**Decision:** (1) ONE ENDPOINT PER RUNG, not one `/enforce` with a `step` body: `POST /v1/admin/users/{id}/warn` + the existing `/suspend` (P1-008) + `POST /v1/admin/users/{id}/terminate`. A single endpoint would audit as one of three actions depending on the body, and the P1-046 audit table requires one unique action per write route (`audit_action_names_are_unique`) — the per-rung shape keeps `user.warned` / `user.suspended` / `user.terminated` each owned by exactly one route. The ladder policy itself is one pure function, `next_step(status, warnings)` (`active` + 0 warnings → warn, `active` + ≥1 → suspend, `suspended` → terminate, `deletion_pending` → nothing), unit-tested in the service — the admin console (Phase 4) calls it to show the next step. (2) DERIVED STATE, no new table: the rung comes from the `users.status` row plus the count of `user.warned` audit rows — the audit trail is the ladder's memory, so a suspension done through the P1-008 endpoint or the P1-090 queue composes with the ladder with nothing to keep in sync. A repeat offender who was warned, suspended and restored goes straight to suspension on the next violation (the count survives the restore). No migration, no config. (3) TERMINATION IS THE P1-007 GRACE, admin-initiated: `request_deletion` (`status = 'deletion_pending'`, `deleted_at = now()`, purge after 30 days) + sessions revoked + queued jobs held + `user.terminated` audited + the `enforcement-termination` mail, all in one transaction. The ladder is sequential: terminate requires `suspended` (422 `PF-2002` on an active account — no jumping rungs), warn requires `active` (422 on a suspended or pending account), and terminating an already-terminated account is a 200 no-op (the P1-007 idempotency). (4) TERMINATION IS STICKY: a `deletion_pending` login cancels the deletion (P1-007) — for a self-requested deletion that is the escape hatch, but for an admin termination it would let the user un-terminate themselves by signing in. The login service tells the two apart from the audit trail (`terminated_by_admin`: the latest of `user.terminated` / `account.delete_requested` for the user) and refuses a terminated account with 403 `PF-1004` (`account_terminated`, new error variant, `login.failure` reason `terminated`) instead of cancelling. A self-requested deletion still cancels on login, exactly as before. (5) EVERY RUNG MAILS: three new templates (`enforcement-warning` / `enforcement-suspension` / `enforcement-termination`, Transactional, uncapped), enqueued in the same transaction as the rung's mutation, payload `{user_id, reason}` — the drain's existing `resolve_recipient` path (load the user, verify `to_hash`) serves them with no drain change. The suspension mail is enqueued by BOTH suspension paths (the P1-008 admin suspend and the P1-090 queue resolve) — the mail belongs to the rung, not to the endpoint — and only on a real transition (a no-op suspend mails nothing). The api-spec's P1-008 sentence "No suspension mail is sent (the spec does not ask for one)" is corrected by this ticket. The route table moves 71 → 73 routes, the OpenAPI handlers 41 → 43, the admin live routes 14 → 16; the API-key matrix gains two `Forbidden` rows, counts 14 Allowed / 37 Forbidden / 8 Unprotected / 12 Ignored.
**Consequences:** An admin can now walk a user down the ladder end to end with the audit row, the mail, and the effect proven at every rung. Honesty: termination does not cancel the user's subscriptions (billing cancellation is the P1-071 support flow — the subscription keeps billing until someone cancels it); the P1-083 auto-suspend path (`abuse.rs`, off by default) calls `users::suspend` directly and mails nothing — a follow-up, not this ticket; the ladder's concurrent-step race (two admins warning/suspending the same user at once) is not locked — each step is its own transaction, so the worst case is two warnings or a warn landing beside a suspend, both audited, never a lost rung.

A job-id lookup resolves through the job's `user_id` — the response names the USER, not the job (the job id is only the key that found them). (4) EVERY LOOKUP AUDITS — INCLUDING MISSES: exactly one `admin.users.lookup` row per call that reaches the service (actor the caller — admin or support — target the resolved user, after `{lookup_kind: "email" | "id" | "job_id", found: true}`); a miss (no such email / id / job) is 404 `PF-2010` (the P1-071 precedent) AND still writes one row (target `null`, after `{lookup_kind, found: false}`) — the access log's job is to show who looked for whom, and a probing pattern (many misses on guessed emails) is visible only if misses are logged. The row is written by the service via `record()` (the P1-108 precedent) and the handler marks the response `AuditHandled` — the route is deliberately NOT added to `audit_action_for` (the P1-046 middleware's contract is writes; its `target_id_from` reads the path, and a query-param lookup has no path id to resolve). NO raw searched value is stored in the audit row (no email, no job id — the resolved user id identifies the access; the searched value is in the request, not the log — privacy by design). Denials (401/403) and validation failures (422) audit NOTHING (the extractor rejects before the handler runs; a 422 means no lookup happened — the P1-108 precedent). No state change, no provider call, no mail. (5) DELETED USERS FOLLOW THE VIEW: the resolve follows `get_admin_user_view`'s rule for the resolved id — if the view 404s a deleted user, the lookup does too (the implementer verifies the view's deleted-user behavior against source and records it; no new rule is invented here). (6) 200, NOT 201: a read (the P1-106 precedent). (7) COUNTS: route table 79 → 80 (new admin row, live; 51 → 52 live, 28 stubs), OpenAPI paths 47 → 48 distinct paths (the new path + no new schema — the response reuses `AdminUserViewResponse`), the authz matrix 27 → 28 rows (20 → 21 live, 7 stubs — the P1-106 row's sibling), the API-key matrix 77 → 78 rows (14 Allowed / 44 Forbidden / 8 Unprotected / 12 Ignored — the new row stays `Forbidden`), the audit_abuse_suite's live writes 11 → 12 (the lookup probe joins — a READ that audits, so the suite's "live writes" count gains one) and its stub writes stay 3, the admin_guard walk 27 → 28 rows (20 → 21 live — the GUARD_ROWS count moves; the guard test's admitted-roles branch gains the lookup). New tests: 5 api-live in `apps/api/tests/user_lookup.rs` (resolve by each of the three keys + audit rows incl. the miss, guard, validation + 404) + 2 service unit tests in `user_lookup.rs` (query validation: exactly-one-of + shapes; audit-row shape incl. the no-raw-value rule); suite total 1296 → 1303 (7 new).
**Consequences:** Support resolves a user from whatever identifier a ticket carries — the email in the message, the id in a log line, the job id in a failure report — and every resolution lands in the access log, so a privacy review can see who accessed which user's data and who probed for users that do not exist. The lookup reuses the P1-106 view, so there is one composite shape and one secret-exclusion proof, not two. The audit row deliberately carries no searched value: the log proves access, it does not become a second copy of the searched email. A bulk-lookup or export endpoint is NOT this ticket — one key per call, one user per call; a list-shaped lookup would need its own audit semantics (one row per result vs one row per call) and an owner decision.

## ADR-0069 — Ticket notes: admin-only append-only notes on users, audited, read through the P1-106 view (2026-11-25, Phase 1)
**Context:** P1-110. The ticket spec ("Admin-only append-only notes on users (jsonb list), audit-tracked; support flow uses them", AC "append-only + audited", Type: feat, area support, deps P1-109) names the storage shape (a jsonb list) and the audit, but not the route, the guard, the note shape, the body limits, what the audit carries, how append-only is enforced rather than merely promised, or how the support flow reads the notes. The pieces already exist: `users` is the row the notes belong to (one column, no new table — the notes are per-user working text, not a queryable entity); the P1-106 view is the support flow's read surface (admin + support already open it for every user); the P1-107 precedent writes a mutation + its audit row in one transaction and marks `AuditHandled`; the P1-099 precedent pins a DB trigger's contract with a live test.
**Decision:** (1) ONE NEW ROUTE, ADMIN SECTION: `POST /v1/admin/users/{id}/notes` — admin-only (`AdminContext`, `AdminUsersWrite` — support is read-only per FR-A-07, so support gets 403 `PF-1002`, the P1-107 precedent; anon 401 `PF-1001`; API key 403). Body `{body}` 1–2000 chars after trimming, no control characters (the P1-008 reason rules with a longer cap — a note is a paragraph, not a reason); unknown keys 422 (`deny_unknown_fields`); all failures collected. Unknown user 404 `PF-2010` (the P1-081 precedent). Any status may be noted — a note on a suspended or deletion-pending user is exactly when support needs to record why (the P1-107 any-status precedent). (2) THE NOTE IS ONE JSON OBJECT: `{id (uuidv7), author_id, author_role, body, created_at}` — the id + `created_at` come from the app clock (the P1-107 frozen-clock precedent: a frozen clock pins the stamp in tests); `author_role` is recorded at write time (roles can change; the history must say who the author was then, not now). (3) STORAGE IS A COLUMN, NOT A TABLE: `users.support_notes` jsonb NOT NULL DEFAULT `'[]'` (migration 20261124210000). One repo fn appends (`support_notes = support_notes || $1::jsonb`, RETURNING the list); no repo fn replaces the column and no endpoint edits or deletes — a wrong note is corrected by appending a new one, so the history stays honest. (4) APPEND-ONLY IS ENFORCED, NOT PROMISED: a BEFORE UPDATE trigger `users_support_notes_append_only` raises unless `OLD.support_notes <@ NEW.support_notes` (jsonb containment — every old element survives in the new list). Reordering passes the trigger (containment is order-insensitive) but the app never reorders — append + oldest-first, so the trigger's job is no-loss/no-edit, not ordering. A live test proves a direct truncation UPDATE fails. (5) THE VIEW IS THE READ: the P1-106 view gains a sixth section `support_notes` (the full list, oldest first) — the support flow already opens the view for every user, so no second GET route and no second shape. The lookup returns the view, so it carries notes too. (6) ONE AUDIT ROW, SAME TX: `admin.users.note_added` in the same transaction as the UPDATE (actor the admin, target the user, before None, after `{note_id, body_chars}`); NO verbatim body in the audit row — the note lives in exactly one place (the column); the audit proves who appended to whom and when, it must not become a second copy of support's working text. The handler marks `AuditHandled`; the route IS in `audit_action_for` (a write with a path id — unlike the P1-109 read, which has no path id to resolve). (7) 200, NOT 201: an admin action on a user (the suspend/warn/grant precedent); the response is `{user_id, notes}` — the full list after the append, oldest first — so the writer sees the result without a second GET. (8) COUNTS: route table 80 → 81 (new admin row, live; 52 → 53 live, 28 stubs), OpenAPI paths 48 → 49 distinct paths (the new path + `TicketNote` / request / response schemas), the authz matrix 28 → 29 rows (21 → 22 live, 7 stubs), the API-key matrix 78 → 79 rows (14 Allowed / 45 Forbidden / 8 Unprotected / 12 Ignored — the new row stays `Forbidden`), the audit_abuse_suite's live writes 12 → 13 (the note probe joins) and its stub writes stay 3, the admin_guard walk 28 → 29 rows (21 → 22 live), role_escalation ALL_ROUTES 28 → 29 + WRITE_ROWS 14 → 15, support_readonly WRITE_ROWS 11 → 12 + admin routes 28 → 29. New tests: 5 api-live in `apps/api/tests/ticket_notes.rs` (guard incl. no-write/no-audit on denial, append shape + audit, append-only order + trigger rejection, view carries notes, validation + 404) + 4 service unit tests in `ticket_notes.rs` (body validation incl. the 2000-char cap; blank/control rejection; note-shape + audit-row shape incl. the no-verbatim-body rule; stored-note round-trip); suite total 1303 → 1312 (9 new).
**Consequences:** Support keeps its working notes on the user, in the open, where the next agent reads them with the view — and the append-only rule is a database fact, not a code promise: no endpoint, no repo fn, and no raw SQL can silently rewrite history. The audit trail proves who wrote when without duplicating the note text. A support-authored note is NOT this ticket — support reads, admin writes; if support ever needs to write, that is a follow-up with its own guard decision (the author_role field already distinguishes the writer). No edit/delete endpoint is ever added on top of this column — the column's contract is append-only from birth.

## ADR-0070 — Support suite: one cross-ticket scenario suite over the P1-106–P1-110 support surface, no new code (2026-11-25, Phase 1)
**Context:** P1-111, the last Phase 1 ticket. The spec ("Role enforcement, audit rows, quota-grant expiry honored", AC "suite green", Type: test, area support, deps P1-110) names the three things to prove but no endpoint, no new shape, and no new registry. The pieces already exist and each already has its own test file: the view (P1-106), the grant (P1-107, incl. its expiry AC), the refund (P1-108), the lookup (P1-109), the notes (P1-110), the attestations list (P1-098), and the role matrix (`support_readonly.rs`, which walks every write route for support). What no file proves is the family AS A STORY: a user hitting a quota wall, support finding them, an admin granting quota, the create going through, a note landing, the whole session audited — and the grant expiring afterwards. That story is this ticket.
**Decision:** (1) TEST-ONLY, NO NEW PRODUCT CODE: no new route, service, migration, table, config, or worker kind — the suite exercises the existing surface through the real HTTP layer only. No registry moves: route table stays 81 (53 live, 28 stubs), OpenAPI stays 49 distinct paths, the authz walk stays 29 rows (22 live / 7 stubs), the API-key matrix stays 79 rows, the audit_abuse_suite's live writes stay 13, the admin_guard walk stays 29 rows. (2) SIX LIVE TESTS in `apps/api/tests/support_suite.rs`, on the frozen clock (Thursday 2026-11-19, 12:00 UTC — the P1-107 precedent; usage seeded for the frozen day; tokens re-issued after any clock advance, the 15-minute-life precedent): `support_suite_role_matrix` (table-driven over 6 endpoints × 5 caller classes — view / lookup / attestations read as support 200; notes / quota-grant / refund write as support 403 `PF-1002`; anon 401 `PF-1001`, plain user 403, admin 200, admin API key 403 on all six; write bodies valid so the denial is the guard, not validation); `support_suite_full_workflow` (Free user at 10/10 images is 429 `PF-3001`; support looks up by email — 200 + one `admin.users.lookup` row; support opens the view — plan free, usage 10/10, no secrets; admin grants 5 images — one `admin.users.quota_granted` row; the user's create reaches the 501 stub with 5 remaining; admin appends a note — one `admin.users.note_added` row; support re-opens the view and reads the note verbatim, oldest first); `support_suite_quota_grant_expiry_honored` (the AC at suite level: a 1 h grant lets the create through; the frozen clock advanced 2 h past expiry, the same create is 429 `PF-3001` again, `unexpired_totals` at the advanced now is (0, 0), the grant row still exists — expiry is a read-time rule, not a delete — and no new audit row appears on expiry, because expiry is not an event); `support_suite_audit_trail` (a lookup hit audits, a lookup miss 404s AND audits with target null, a view read audits nothing, a grant + a note + a refund audit exactly one row each with the right actor/target, and a denied support write audits nothing); `support_suite_refund_guides_and_changes_nothing` (the refund returns the checklist — dashboard deep-link + note, four steps all `done: false`, `amount` / `invoice_or_payment_id` null — the subscription row is byte-identical afterwards, the refund adds no mail (registration's welcome mail is the only mail), exactly one `billing.refund.requested` row exists, and a second call writes a second row); `support_suite_attestations_visible_to_support` (eleven seeded attestations for one user, one second apart: support lists them and reads the newest row flagged — `velocity_count` 11, `flag_reasons` non-empty — the rest 10..1 unflagged, and `?flagged=true` returns only the flagged row). (3) RE-PROOF IS INTENDED: the suite deliberately re-proves per-ticket ACs (grant expiry, note visibility, refund checklist) at the story level — the per-ticket files stay the unit of record; this suite is the regression net that fails first when the family drifts, and it is the only file that proves the three spec phrases together. (4) COUNTS: 6 new live tests, 0 unit tests; suite total 1312 → 1318 (6 new).
**Consequences:** Phase 1 closes with the support family proven as one workflow, not five separate endpoints — the next reader who changes a guard, an audit action, or the grant's expiry rule has one file that catches the drift. The suite proves nothing about the removal engine (job creation is still the 501 stub; the "create reaches the stub" step is a quota-gate proof, not a job proof), and it proves nothing new about any single endpoint beyond its own file — that is the point: it is a net, not a feature.
