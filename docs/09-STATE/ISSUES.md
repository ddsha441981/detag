### PERF-001 [hardening] Synchronous Argon2id verify blocks tokio workers — a burst of concurrent logins 500s on pool timeout (P1-004)
- Date: 2026-11-13 · Ticket: P1-004
- Finding: the login service verifies the password inline (`verify_password` in the async handler). Argon2id is ~250 ms of synchronous CPU per verify. On this VM (2-worker runtime, 10-connection pool), twenty concurrent logins starve the workers: the failure transactions cannot drain (each statement waits for worker time), pool acquires hit the 5 s timeout, and the login 500s — proven by a scratch run that reproduced the exact flow with the real error (`PoolTimedOut` at the very first query, 8/20 ok; the repo layer alone is clean 20/20, counter exactly 20). An HTTP-level concurrent race test was tried at 20, then 8, then 4 concurrent logins and flaked in the full-binary run (the other five lockout tests' verifies add load), so the race proof lives at the repo layer (`concurrent_counter_records_never_lose_an_increment` in `tests/lockout.rs`) and the HTTP tests prove the wiring sequentially.
- Why it matters beyond tests: in production the per-account bucket (10 burst) trips before twenty concurrent logins for one account, but a burst across MANY accounts (e.g. a class logging in at once) still runs many concurrent verifies on the same workers — the same starvation can 500 some of them if the pool is small relative to the burst. The idiomatic fix is `tokio::task::spawn_blocking` for the verify (and the dummy-hash verify), or a larger pool + more workers; it is a hardening change, out of P1-004's scope.
- Status: open — hardening candidate (Phase 5 or a performance ticket); the lockout itself is correct and race-safe.

### ASSUMPTION-012 [assumption] `db_health` takes the full 2 s probe timeout on an unreachable database (P0-066)
- Date: 2026-11-12 · Ticket: P0-066
- Assumption: on a dead database the db probe does NOT fail fast — it reports ~2000 ms latency via the timeout arm. Verified in the vendored sqlx-core 0.9.0 source (`pool/inner.rs`): `acquire` retries transient connection errors in a backoff loop (10 ms doubling, capped at deadline/5) until the acquire deadline, so `SELECT 1` against a closed port keeps retrying until this probe's own 2 s `tokio::time::timeout` fires. The probe is therefore slow-but-bounded on a down DB by design; `/readyz` on a dead database takes ~2 s (probes run concurrently, so the total is ~2 s, not ~8 s). The `db_health_down_on_unreachable_database` test asserts `latency_ms <= 2050` (timeout + scheduling slack), not `< 2000`. A fail-fast db probe (raw TCP pre-check like the redis probe) is a possible future optimisation, not a P0-066 gap.
- Status: open

### SHUTDOWN-001 [bug] api + worker self-terminate ~30 s after startup with no signal (P0-090) — FIXED
- Date: 2026-11-12 · Ticket: P0-090 · Severity: S2 (would restart-loop both services in production)
- Symptom: during the `just smoke --skip-up` proof, the api and worker died ~30 s after startup with no signal sent — api: "detag-api shutdown timed out after 30s; forcing exit", worker: "drain timed out" exactly 30.066 s after "started", both exit 1. Three identical deaths across three proof attempts; the ping leg could not complete because the binaries died during the smoke-ping cargo build.
- Cause: `tokio::time::timeout(SHUTDOWN_TIMEOUT, ...)` wrapped the WHOLE server/monitor run from startup, not the post-signal drain — api `main.rs` (`timeout(30s, join!(api_server, metrics_server))`) and worker `main.rs` (`timeout(drain_timeout, monitor.run_with_signal(...))`). With no signal the servers run forever, so the timeout fired at 30 s unconditionally. Nothing had ever run either binary past 30 s on this VM (dev runs, probes and tests all finish inside the window), so the bug was invisible until the smoke proof.
- Fix (in the P0-090 commit): both mains now spawn the servers/monitor as a task, wait for the signal with no timeout, and apply the timeout only to the drain after the signal; a server/monitor erroring on its own still ends the process promptly (new `End`/`Drain` enums, single exit path). Regression test `stays_up_past_shutdown_timeout_without_signal` (api, ~32 s: still answers /healthz past the timeout, then SIGTERM exits 0). The smoke proof then went green end-to-end. Side fix in the same test file: each test now takes its own `PF_METRICS_PORT` (parallel runs previously shared the default 9090 and the second api failed to bind).
- Status: fixed (P0-090) — the regression test + the CI smoke job guard it (the CI smoke build alone exceeds 30 s, so a recurrence fails the job).
