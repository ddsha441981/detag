# Security Testing Plan

Executed as tickets in Phase 1 (authz), Phase 2/3 (upload abuse), Phase 5 (full sweep). Each item = a named test that lives in CI, not a one-off manual check.

Threat model: `docs/threat-model.md` — the living threat model this plan tests against. If a test here covers a threat, the threat's ID (T1–T17) is the cross-reference.

## Authorization matrix sweep (IDOR)

For every `/v1` endpoint × role {anonymous, user-A, user-B, support, admin, api-key-scoped}: assert allowed matrix. Auto-generated table test in `apps/api/tests/authz_matrix.rs`; adding an endpoint without a matrix row fails the test (registry pattern: routes self-register their matrix entry).

## Session & token tests

- Refresh rotation: reuse of rotated refresh ⇒ whole family revoked (PF-1007), event logged.
- JWT: alg-confusion attempt (alg:none, HS/RS swap) rejected; exp/nbf enforced; kid confusion rejected.
- Password flows: reset token single-use; old password invalid after reset; email-verification enforced before jobs.
- Cookie flags: Secure, HttpOnly, SameSite=Lax asserted in integration tests.
- Login (P1-003, T17): unknown email and wrong password answer byte-identical 401 `PF-1001` (the test compares the two bodies — no enumeration); constant-time verify via the precomputed dummy hash (an unknown email costs one Argon2id verify, like a wrong password); per-account bucket (10 burst / 1 per min) trips pre-auth — a correct-password attempt after the limit is 429 `PF-3007` with `Retry-After`; per-IP bucket trips on login too (the middleware's bucket, proven with a per-test XFF address).
- JWT claims (P1-013): the claims shape is locked by test — the issued token's raw payload has exactly `{sub, role, ver, jti, exp, iat, iss, aud}` (a stray claim would fail the test), `ver` = 1, `iss` = `"detag"`, `aud` = `"detag-api"`, `exp - iat` = 900, `jti` a UUID, no `impersonator_id` on a normal token; the JOSE header is `alg: HS256`, `typ: JWT`, `kid` = the first 16 hex chars of the secret's sha256. The verifier rejects a wrong issuer, a wrong audience, a future version, and a foreign `kid` (each asserted with a hand-built token — all 401 `PF-1010`); a pre-P1-013 token (`{sub, role, exp, iat}` only, no header `kid`) still verifies (asserted — the new fields default on decode). The impersonation token's payload carries `impersonator_id` (asserted) and the same header `kid`.
- Lockout (P1-004, T17): five failures lock the account AND the IP — the next login (even with the correct password) is 423 `PF-1008` with `Retry-After` ≈ 60 s (the first backoff step; the full curve 60 → 120 → … → 3600 is proven exactly by the unit test in `crates/core/src/lockout.rs`), and a further attempt while locked does not extend the lock; a success resets both counters (four failures + success + five failures locks, never earlier); the lockout mail is queued exactly once per episode (`lockout-notice`, `login.locked` audited); five failures from one IP for different emails lock the IP — a fresh account from that IP is 423; twenty concurrent failures never lose an increment (counter ends at exactly 20, lock at the 1-hour cap); registering an email clears a counter the address accumulated before it existed.
- Profile + auth extractor (P1-005): `GET`/`PATCH /v1/me` without a credential, with a malformed JWT, or with a valid JWT for an unknown user is 401 `PF-1001`; an expired JWT is 401 `PF-1011` (the extractor's own unit test proves the three no-DB rejections; the integration tests prove the happy path and the unknown-user case through the real router). A Bearer API key or a session cookie is 401 `PF-1001` today (no key table read yet; the cookie leg is P1-016). The profile never leaks the password hash (asserted on the GET body); the email-change intent is duplicate-checked (409 `PF-2011`) and the `profile.update` audit carries the pending email as sha256 only.
- Email change (P1-006, T18): setting a pending email mints an `email_change` token + queues the verification mail to the new address and the takeover alert to the old address (the alert carries no token and never names the new address — asserted on the outbox rows); confirming swaps the email atomically (consume + swap + audit in one tx) and verifies the new address; a registration token at confirm is 401 `PF-1010` (wrong purpose, not consumed — asserted: the token still verifies afterwards); an expired change token is 401 `PF-1011` (not consumed); a cleared intent deletes the change token (confirm then 401s); an address taken meanwhile is 409 `PF-2011` with the token surviving (tx rolled back) and the intent still pending; a resend-verification kills a live change token (one live token per user — the pending intent survives and is re-triggered by clearing + re-setting).
- Account deletion (P1-007, T19): `DELETE /v1/me` requests deletion (204, `status = 'deletion_pending'`, `deleted_at` set — the account is NOT deleted yet, GET still works and shows the grace); a second DELETE is a no-op (grace runs from the first request — asserted: no refreshed `deleted_at`, no second audit row, no second mail); a login during the grace cancels it (asserted: status active, `deleted_at` cleared, one `account.delete_cancelled` audit row, and a second login after the cancel audits nothing more); the purge (`detag-gc --purge-users`) hard-deletes past-grace accounts with the full cascade (asserted: sessions, jobs, uploads, job events, attestations, subscriptions, usage counters, idempotency keys and verification tokens all gone; audit rows survive with the actor id intact — migration 20261113062352 dropped the actor FK and made the job_events / attestations triggers UPDATE-only, because the old contract blocked every purge of a user with history; see `migration_purge_cascade_triggers.rs`).
- Admin suspend / restore (P1-008, T20): an admin suspends a user (200, status `suspended`, both live sessions revoked — asserted via `sessions::list_for_user`, every `revoked_at` set — and every queued job held, `queued` → `held`; the `user.suspended` audit carries the reason + `{sessions_revoked, jobs_held}` in `after`); a non-admin gets 403 `PF-1002`, no credential gets 401 `PF-1001`, an unknown target gets 404 `PF-2010`, a missing or blank reason gets 422 `PF-2002` (asserted: the target is untouched by the rejection); suspending an already-suspended account is a 200 no-op (asserted: exactly one `user.suspended` audit); a restore returns the account to `active`, releases held jobs to `queued`, and leaves sessions revoked (asserted: the session row still has `revoked_at` — the user logs in again); restoring a non-suspended account is a 200 no-op (asserted: no `user.restored` audit); a suspend cancels a pending deletion (asserted: status `suspended`, `deleted_at` cleared); a suspended login is 403 `PF-1003` after a correct password and the generic 401 `PF-1001` after a wrong one (asserted: the suspended attempt audits `login.failure` with reason `suspended`); after a restore the login works again. The residual window is documented, not tested away: the access token already issued stays valid until it expires (≤ 15 min) — the extractor does not check status. Bonus finding (P1-008): the error mapper kept the framework's 400 wire status while the problem body said 422 — a malformed-UUID path param answered 400 with a 422 body; the mapper now stamps the wire status from the problem (its own docs already promised "a framework 400 becomes a 422 problem"), proven by the malformed-UUID test (422 `PF-2002`); the 404/413/415 mappings are unaffected (their problems carry the same status the framework sent).
- Admin user search (P1-009): `GET /v1/admin/users` lists users in `created_at` order (oldest first) with cursor pagination — five users, `limit=2`, walk all three pages in order with no duplicates and no skipped rows (asserted: the union of the pages is exactly the five, and the third page has no `next_cursor`); `?query=` filters by email prefix, display-name prefix (asserted: a query matching only the display name narrows to that user), and id prefix (asserted: every returned id carries the prefix); a query with no match is 200 with `items: []` and no cursor; `limit=0` clamps to 1 (asserted: one item + a cursor); a tampered cursor is 422 `PF-2002`; a non-numeric `limit` is 422 `PF-2002` (the `Query` extractor's rejection, rewritten by the error mapper); support may search (200 — read-only role), a plain user gets 403 `PF-1002`, no credential gets 401 `PF-1001`; a user with a live Pro subscription + today's usage row shows `plan: "pro"`, `images_used_today: 3`, `video_seconds_used_today: 120` (asserted), while users without either show `plan: "free"` and zeros. Test-isolation lesson: the harness DB persists across runs, so a test prefix must be unique per RUN — the first 8 hex chars of a UUID recur every ~65 s (they are the top of the unix-ms timestamp), and the previous run's users leaked into this run's filtered search until the prefix carried a full UUID (the email then carries no second UUID, or the local part exceeds the validator's 64-character cap — that was the earlier 422).
- Impersonation (P1-010, T21): an admin impersonates a user (200, `token_type: "Bearer"`, `expires_in: 900`, `impersonator_id` = the admin, `user_id` = the target; the token's claims are verified directly — `sub` + `role` are the target's, `impersonator_id` is the admin, `exp - iat` is exactly 900); the token acts as the target (`GET /v1/me` returns the target's profile, asserted); the token cannot reach admin endpoints (asserted: suspend is 403 `PF-1002`, the admin user list is 403 `PF-1002` — reads included); support gets 403 `PF-1002` (impersonation is a write), a plain user gets 403 `PF-1002`, no credential gets 401 `PF-1001`, an unknown target gets 404 `PF-2010`, a missing or blank reason gets 422 `PF-2002` (asserted: no `user.impersonated` audit for the rejections); the impersonation is audited once (`user.impersonated`, actor = the admin, target = the user, the reason verbatim, `after.expires_in` = 900); an expired impersonation token is 401 `PF-1011` (asserted with a token minted 60 s in the past — auto-expiry is the JWT `exp`, leeway 0; the service only ever issues 15-minute tokens). The banner contract is documented in the api-spec (the console MUST show both ids for the whole session); the per-action dual-id audit convention is P1-011's scope.
- Impersonation audit tests (P1-011, T21): every impersonated action's audit row carries BOTH ids — an impersonated profile update audits `profile.update` with `actor_user_id` = the admin and `target_id` = the user (asserted, incl. `after.display_name` = the new name, and `GET /v1/me` under the token shows it — the action worked as the user), and an impersonated deletion request audits `account.delete_requested` the same way (asserted; the account is `deletion_pending` afterwards); a normal (non-impersonated) profile update still audits actor == target == the user (regression asserted). The `user.impersonated` row itself is checked field by field (action, actor, `target_type: "user"`, target, `before` is None, `after.expires_in` = 900, reason verbatim). The admin block is proven on every live admin route (restore + impersonate + the user list, on top of P1-010's suspend — all 403 `PF-1002`; the stub admin routes carry no guard yet, their tickets add one with the real handler). An expired impersonation token cannot reach admin endpoints either — it is 401 `PF-1011`, not 403 (expiry is checked before the guards run, asserted on suspend + the user list). Impersonating an admin target is still blocked (asserted: the token's role is `admin`, but the block is on the impersonator marker, not the role — the user list is 403 while `GET /v1/me` works as the target admin). The code change this ticket needed: the audit actor is threaded through the profile + deletion services (`AuthContext::audit_actor_id` — the impersonator when impersonating, else the user; the handlers pass it explicitly, and the `ref user` borrow keeps `auth` usable after the unwrap).

## API & webhook hardening

- Body caps per route class (P0-104): auth/meta 64 KiB, jobs/admin 1 MiB, billing (webhooks) 256 KiB; over-cap is 413 PF-2003, tested per class. Uploads are exempt (bytes never transit the api).
- Dimension caps (P0-104, FR-U-04): 8000x8000 per side, 64 MP total, enforced at job-create by `validate_dimensions` (PF-2005, 413, fail-closed on missing dimensions); the sniff-time dimension check in the abuse table above lands with intake (Phase 2/3).
- Webhook SSRF: endpoint URL must resolve to public HTTPS; private/link-local CIDRs denied; redirect-following disabled; tested with a listener on 169.254.169.254-style address.
- Outbound webhook HMAC: constant-time compare; replay window enforced; tampered payload rejected.
- Idempotency: replayed Idempotency-Key returns original response; concurrent duplicates create one job (integration test with racing requests).
- Rate limits: per-IP + per-route token buckets enforced by the middleware (P0-103; race-safe — no over-admission under concurrency, proven by test); per-account + per-key tiers land with Phase 1 auth; lockout backoff curve asserted.
- Injection: sqlx parameterized everywhere (CI grep forbids `format!`-built SQL); no string-built shell calls (ffmpeg args as argv array, never shell string).

## Headers & transport

CSP (web), HSTS (prod only — dev is plain http, so dev responses carry the rest of the table but no HSTS), X-Content-Type-Options, Referrer-Policy, frame-ancestors none for app routes; the Swagger UI at `/docs` gets its own same-origin CSP (the api's `default-src 'none'` would block its JS) — asserted by a route test against a header table. TLS terminated at caddy in prod; internal services never exposed (compose networks: `internal` vs `edge`).

## Secrets & supply chain

gitleaks CI; `cargo deny` advisories+licenses gate; Dependabot-style weekly bump window (Phase 5 cadence); no secrets in fixtures, logs, or error messages (test asserts error bodies contain no stack traces in prod profile).
