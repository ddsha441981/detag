# Security Testing Plan

Executed as tickets in Phase 1 (authz), Phase 2/3 (upload abuse), Phase 5 (full sweep). Each item = a named test that lives in CI, not a one-off manual check.

Threat model: `docs/threat-model.md` — the living threat model this plan tests against. If a test here covers a threat, the threat's ID (T1–T23) is the cross-reference.

## Authorization matrix sweep (IDOR)

For every `/v1` endpoint × role {anonymous, user-A, user-B, support, admin, api-key-scoped}: assert allowed matrix. Auto-generated table test in `apps/api/tests/authz_matrix.rs`; adding an endpoint without a matrix row fails the test (registry pattern: routes self-register their matrix entry).

## Session & token tests

- Refresh rotation: reuse of rotated refresh ⇒ whole family revoked (PF-1007), event logged.
- JWT: alg-confusion attempt (alg:none, HS/RS swap) rejected; exp/nbf enforced; kid confusion rejected.
- Password flows: reset token single-use; old password invalid after reset; email-verification enforced before jobs.
- Cookie flags: Secure, HttpOnly, SameSite=Lax asserted in integration tests.
- Login (P1-003, T17): unknown email and wrong password answer byte-identical 401 `PF-1001` (the test compares the two bodies — no enumeration); constant-time verify via the precomputed dummy hash (an unknown email costs one Argon2id verify, like a wrong password); per-account bucket (10 burst / 1 per min) trips pre-auth — a correct-password attempt after the limit is 429 `PF-3007` with `Retry-After` and the trio, and the `X-RateLimit-Limit` names the account bucket (asserted: "3" with a burst-3 test bucket — P1-020); per-IP bucket trips on login too (the middleware's bucket, proven with a per-test XFF address).
- JWT claims (P1-013): the claims shape is locked by test — the issued token's raw payload has exactly `{sub, role, ver, jti, exp, iat, iss, aud}` (a stray claim would fail the test), `ver` = 1, `iss` = `"detag"`, `aud` = `"detag-api"`, `exp - iat` = 900, `jti` a UUID, no `impersonator_id` on a normal token; the JOSE header is `alg: HS256`, `typ: JWT`, `kid` = the first 16 hex chars of the secret's sha256. The verifier rejects a wrong issuer, a wrong audience, a future version, and a foreign `kid` (each asserted with a hand-built token — all 401 `PF-1010`); a pre-P1-013 token (`{sub, role, exp, iat}` only, no header `kid`) still verifies (asserted — the new fields default on decode). The impersonation token's payload carries `impersonator_id` (asserted) and the same header `kid`.
- Refresh rotation (P1-014, T22): presenting a live refresh token rotates in the same family (asserted: two rows, one `family_id`, the old row `revoked_at` set + `replaced_by` = the new row's id, the new row live; `session.refreshed` audited with the family id; the new access token verifies and works on `GET /v1/me`); rotations chain (asserted: A → B → C, three rows, one family, two `session.refreshed` audits); presenting an already-replaced token is a reuse attack — 401 `PF-1007` (asserted), the whole family revoked (asserted: every row `revoked_at` set), `session.refresh_reused` audited once with `after.sessions_revoked` = 1, and the security email queued (`refresh-reuse-alert`, asserted on the outbox by the email hash); the new token from the rotation is then dead too — presenting it is the generic 401 `PF-1001`, not a second PF-1007 (asserted: no second reuse audit — it was revoked, not rotated). Unknown / missing-cookie / expired / revoked tokens are all the generic 401 `PF-1001` (asserted, with no reuse audit and no mail); an impersonation token in the cookie is 401 `PF-1001` (asserted — no session row behind it, so the hash lookup fails).
- Cookie + bearer dual auth (P1-016, T23): the Bearer path authenticates (asserted: `GET /v1/me` with only the access token → 200); a genuine, live refresh token in the cookie as the SOLE credential 401s (asserted: login, then `GET /v1/me` with only the `detag_refresh` cookie → 401 `PF-1001` — the refresh token is not an access credential, even when it is real); Bearer + cookie authenticates by Bearer (asserted: 200); a forged cookie alongside a valid Bearer token does not fail the request (asserted: 200 — the cookie is never validated as an access credential); a Bearer API key 401s (asserted: 401 `PF-1001` — API keys are E1.4); `GET /v1/auth/refresh` is 405 (asserted — a top-level navigation, which DOES carry a `SameSite=Lax` cookie, cannot rotate a session: there is no state-changing GET).
- Logout (P1-017, T22): `POST /v1/auth/logout` revokes the presented session (asserted: the row is `revoked_at`-set, `session.logged_out` audited with the session id, the response clears the cookie with `Max-Age=0`); a second logout of the same session is a no-op 204 with no second audit (asserted); no cookie or an unknown token → 401 `PF-1001` (asserted); a revoked refresh token cannot rotate (asserted: refresh with the logged-out token → 401 `PF-1001`); the access token already issued stays valid until expiry (asserted: `GET /v1/me` with it → 200 — the residual window, documented not hidden); another session of the same user is unaffected (asserted: its refresh still rotates). `POST /v1/auth/logout-all` revokes every session (asserted: all 3 rows `revoked_at`-set — A replaced, B, C — `session.logged_out_all` audited once with `sessions_revoked` = 2, the sessions THIS call revoked; A was already revoked by the rotation and is not counted twice); no refresh token rotates afterwards (asserted: B and C → 401 `PF-1001`); a replaced token presented after logout-all is still a reuse detection (asserted: A → 401 `PF-1007` — the row still carries `replaced_by`, logout-all does not erase the rotation history); a cookie-only caller gets 401 `PF-1001` (asserted — the Bearer extractor rejects a bare cookie); no credential → 401 `PF-1001` (asserted).
- Revoke on password change (P1-018, T22): the service revokes every live session except the current one (asserted: 4 rows — A replaced, B, C, D kept — the call returns 2, B + C revoked, D live, A still revoked and not counted twice; the audit `session.revoked_on_password_change` carries `sessions_revoked` = 2 + the kept session id; the digest mail `new-login-digest` is queued with `{user_id, sessions_revoked}`); the kept session still rotates through the real refresh endpoint (asserted: 200) while a revoked one answers the generic 401 `PF-1001` (asserted). The reset case (`None` — no current session) revokes everything (asserted: 2/2 rows, audit + mail). No sessions at all: no audit, but the digest mail is still queued (asserted — the mail notifies about the password CHANGE, the audit records the REVOCATION). The HTTP wiring is now landed — the reset flow (P1-025) calls the service; no change-password route exists yet.
- Session listing (P1-019, T22): `GET /v1/me/sessions` lists live sessions newest first (asserted: 2 items — the Firefox login first — each with the parsed device label, the ip hash, created, last_seen, expiry, id; the raw User-Agent is never echoed; a fresh session's `last_seen` equals its `created_at`); revoked and expired sessions are excluded (asserted: 1 item left after a logout + a seeded expired row). `DELETE /v1/me/sessions/{id}` revokes one (asserted: the token is dead — refresh → 401 `PF-1001` — while the other still rotates; `session.revoked` audited with the session id; a second DELETE is a no-op 204 with no second audit); unknown id or another user's id → 404 `PF-2010` (asserted — no enumeration). Throttled `last_seen` (the AC, asserted at the row level): a session backdated 10 minutes advances on refresh (10 > 5-minute throttle); a session backdated 1 minute does NOT advance (1 < 5).
- Lockout (P1-004, T17): five failures lock the account AND the IP — the next login (even with the correct password) is 423 `PF-1008` with `Retry-After` ≈ 60 s (the first backoff step; the full curve 60 → 120 → … → 3600 is proven exactly by the unit test in `crates/core/src/lockout.rs`), and a further attempt while locked does not extend the lock; a success resets both counters (four failures + success + five failures locks, never earlier); the lockout mail is queued exactly once per episode (`lockout-notice`, `login.locked` audited); five failures from one IP for different emails lock the IP — a fresh account from that IP is 423; twenty concurrent failures never lose an increment (counter ends at exactly 20, lock at the 1-hour cap); registering an email clears a counter the address accumulated before it existed.
- Brute-force limiter wiring (P1-020, T17): the per-IP login bucket (`login-ip`, 20 burst / 10 per min, keyed by the sha256 of the client IP) trips across accounts — three wrong-password logins for three different accounts from one IP, then a fourth account with the CORRECT password is 429 `PF-3007` with `Retry-After` and the trio, the Limit naming the login-IP bucket (asserted: "3" with a burst-3 test bucket) and no session created; the lockout is checked FIRST, so a locked login answers 423 and never spends a bucket token (a 429 cannot mask the 423 — a locked attempt never reaches the bucket, so the two denials can never coincide); the register bucket (`register-email`, 5 burst / 1 per min, keyed by the sha256 of the email) trips per address — 1 creation (201) + 4 duplicates (409, which spend the bucket too) then the 6th attempt is 429 with the trio naming the register bucket (asserted: "5"); the reset bucket (`reset-account`, 10 / 1) exists in config + policy but nothing spends from it yet — the reset flow (P1-025) wires the check; concurrency-safe (asserted: 50 concurrent spends per service bucket admit exactly the burst — login-account 10, login-ip 20, register-email 5, reset-account 10 — the same Lua atomicity as the middleware buckets). Bug found by the login-IP test (P1-020): the middleware unconditionally overwrote the `X-RateLimit-*` trio on every response, so a service denial's 429 carried the middleware IP bucket's numbers (Limit 120) instead of the denying bucket's (Limit 3) — the middleware now stamps only when the handler has not already, proven by the Limit assertions on the account + login-IP + register denials.
- Token revocation cache (P1-021, T22): the epoch kills pre-change tokens (asserted: after the password-change service call, the old access token → 401 `PF-1010` on `GET /v1/me`, and a fresh login after a 1.1 s sleep — the bump's second must pass before a new token's `iat` clears it — → 200; the `revoked_before` column is set on the user row, asserted in the password-sessions tests for all three cases — change, reset, and no-sessions); the jti denylist kills exactly the listed token (asserted: `revoke_jti` then the token → 401 `PF-1010`, another token of the same user → 200); logout-all denylists the presented token only (asserted: the presented token → 401 `PF-1010` after logout-all, another device's token → 200); a legacy token without a `jti` skips the denylist but the epoch still covers it (asserted: the legacy token → 200 before the bump, 401 `PF-1010` after it). Bug found by the epoch tests (P1-021): the epoch comparison was strict `<` against the floored second, which has a one-second hole — a token minted in the same second as the bump shares the bump's second (`iat == floor(bump)` is not `< bump`), so the pre-change token survived; the comparison is now `<=` (fail closed on the boundary second — a post-change token minted in the same second is denied too and self-heals via refresh, proven by the 1.1 s sleep in the fresh-login assertion). Perf (measured, not claimed): the denylist GET is mean ~127 µs, p50 ~114 µs, p99 ~378 µs (miss: p50 ~111 µs, p99 ~500 µs) on local Redis, 200 sequential calls — ~0.1–0.5 ms per authenticated request, negligible next to the Postgres user lookup; the epoch check adds no query at all.
- JWT verification extractor (P1-022, T20/T22): the extractor verifies signature + expiry + not-before (leeway 0 — a future-`nbf` token is 401 `PF-1010`, immature not expired, asserted in the core unit test + the extractor integration test; a pre-P1-022 token without `nbf` still verifies — it defaults to 0, asserted); a tampered token is rejected (asserted: one flipped payload character → 401 `PF-1010`; the same claims signed with another secret → 401 `PF-1010`; the untouched token still works afterwards); the role is re-read from the database on every request (asserted: demote an admin in the DB → the SAME token gets 403 `PF-1002` on the admin list at once while `GET /v1/me` still works; promote back → 200 again; a token minted while the user was a plain user gains admin access the moment the row says admin; a token whose embedded `role` claim says "admin" for a plain user is still treated as that user — the claim is never trusted, asserted: profile 200, admin list 403 `PF-1002`); an API key answered 401 `PF-1001` then (asserted — the key leg was the E1.4 integration point; P1-034 fills it in — see the P1-034 bullet below). The locked claims shape is now nine keys (`nbf` = `iat` on every minted token, asserted by the shape test).
- API-key auth extractor (P1-034, T20): a live key with the route's scope reaches the handler (asserted: `jobs:write` → `POST /v1/jobs` 501, `jobs:read` → `GET /v1/jobs` 501, `webhooks:manage` → `GET /v1/webhook-endpoints` 501 — the stub's 501 is the proof auth passed); a key without the scope is 403 `PF-1002` (asserted: `jobs:read` → `POST /v1/jobs`, `jobs:write` → `GET /v1/jobs`, `jobs:write` → `GET /v1/webhook-endpoints`, `jobs:read` → `POST /v1/jobs/{id}/attestation` — scopes are independent, write does not imply read); a key on a route the table does not name is 403 `PF-1002` (asserted: a key carrying all three scopes → `GET /v1/me`, `GET /v1/admin/users`, `POST /v1/api-keys` — keys cannot mint keys, fail closed); an unknown key is the generic 401 `PF-1001` (asserted: a random `pf_live_*` string); a revoked key reads exactly like an unknown one (asserted: mint → use → revoke the row → 401 `PF-1001`); a key whose owner is not `active` is 401 `PF-1001` (asserted: suspend the owner → the key 401s — ADR-0024, suspend revokes sessions but not keys and a key has no expiry, so without this a suspended user's key would work forever); a key minted by an admin user cannot reach admin routes (asserted: admin owner + all scopes → `GET /v1/admin/users` 403 `PF-1002` — the table names no admin route and the guards reject a key-carrying context as a second line). `last_used_at` is throttled (asserted: NULL before first use → stamped on first verified use → a scope-denied call leaves it alone → a second verified use inside the 300 s window leaves it alone → ageing it 10 minutes and using again re-stamps it). The scope table itself is unit-tested (13 mapped routes + 7 unmapped/wrong-method cases) and `require_scope` is unit-tested (JWT callers pass, scoped keys pass, unscoped keys and unverified contexts 403).
- API-key rotation (P1-035, T20): rotating mints a replacement secret (same name + scopes, new row, new prefix) and stamps the old row's `expires_at` to `now + PF_API_KEY_ROTATION_OVERLAP_SECS` (default 24 h) — the response carries the NEW secret once (asserted: 201, new secret differs, same name/scopes, new id/prefix, old row `expires_at` set, new row NULL, `api_key.rotated` audited with both ids/prefixes and no secret/hash); the old secret stays valid inside the window (asserted on a frozen clock: old + new both reach the scoped jobs stub at 501, old still 501 one second before the deadline) and dies past it (asserted: old is the generic 401 `PF-1001` while the new secret still reaches the stub); rotation is exempt from the 10-live-keys cap (asserted: rotating at a full 10 succeeds) but the old row still counts during the overlap (asserted: 9 keys + rotate, then a 10th create is 409 `PF-2011`) and stops counting after it (asserted: past the window the 10th create is 201 again); a key cannot rotate (asserted: a live key as the credential is 403 `PF-1002`, no credential is 401 `PF-1001`); unknown id, another user's id, and a revoked key are all 404 `PF-2010` (asserted — no enumeration). The repo layer proves the expiry rule directly (asserted: a row past `expires_at` does not verify and stops counting, a row inside its window still verifies and counts, `by_id_for_user` still reads dead rows for the service's decision).
- Auth integration suite (P1-023, T1/T22/T23): the whole lifecycle in one scenario on a frozen `ManualClock` (asserted: register → verify → login → refresh → rotate → reuse → fresh login → logout, with the session list proving each step — 1 live session after login, still 1 after rotation, 0 after logout); verify is single-use (asserted: the second verify of the same token is 401 `PF-1010`); role refresh on the same token (asserted: promote → admin list 200, demote → 403 `PF-1002`); reuse is 401 `PF-1007` with the whole family revoked (asserted: the fresh token from the rotation is then the generic 401 `PF-1001`, `session.refresh_reused` audited, the rotated row `revoked_at`-set) while the access tokens live out their residual window (asserted: `GET /v1/me` with the newest access token still 200 after the reuse); logout kills the refresh token (asserted: refresh → 401 `PF-1001`) but not the access token (asserted: still 200 — the residual window, documented not hidden). Clock-injected expiry (asserted by moving the frozen clock, never by waiting): the access token dies 16 minutes after issue (401 `PF-1011`) while the session still refreshes; the session dies 31 days after login (refresh → 401 `PF-1001`, access → 401 `PF-1011`); the verification token dies 25 hours after register (401 `PF-1011`). Tampering (asserted: flipped payload byte → 401 `PF-1010`; foreign secret → 401 `PF-1010`; garbage → 401 `PF-1010`; a future-`nbf` token → 401 `PF-1010`, then 200 once the clock reaches its `nbf`). The clock threading behind it: the `_at` JWT forms (asserted in the core unit tests — issue/verify at an injected instant, expiry at `exp + 1s`, future-`nbf` immature then mature, `_at` agrees with the wall-clock forms) and every auth-path expiry reading `state.clock.now()` instead of the wall clock (login, refresh, verification tokens, extractor, impersonation issue, jti-denylist TTL, session listing).
- Forgot / reset password (P1-025, T17/T22): `POST /v1/auth/forgot-password` is 204-always (asserted: an unknown email answers exactly like a known one — same 204, empty body — with no reset mail queued for its hash and the request audited as `password.reset_requested` with the email hash only); a known email queues the reset mail (asserted: one `password-reset` outbox row with `{user_id, token}`) and a second forgot kills the first token (asserted: the first token → 401 `PF-1010`, the second → 204 — one live token per user, the P1-006 rule across purposes). `POST /v1/auth/reset-password` changes the password and revokes EVERY session (asserted: login with the old password → 401, with the new one → 200; the old refresh token → 401; the old access token → 401 `PF-1010` on `GET /v1/me` — the epoch bump; the fresh login's session is the only live one; `password.reset` + `password.reset_requested` + `session.revoked_on_password_change` audited; the `new-login-digest` mail queued). The token is single-use (asserted: the second reset with the same token → 401 `PF-1010`); expired → 401 `PF-1011` (asserted with a seeded expired row, and with the frozen clock: alive at T0 + 29 min, dead at T0 + 31 min — the 30-minute TTL); a registration token at reset → 401 `PF-1010` AND survives (asserted: it still verifies the email afterwards — wrong purpose is not consumed); an unknown token → 401 `PF-1010`; a short new password → 422 `PF-2002`. The reset-account bucket trips (asserted: 10 forgots for one address — unknown — then the 11th is 429 `PF-3007` with `Retry-After` and the trio naming the reset-account bucket, Limit "10"). A reset un-locks the account (asserted: 5 failed logins → the correct password is 423 `PF-1008`; forgot + reset → login with the new password → 200). An unverified user can reset (asserted: fresh unverified user → forgot → reset → login works).
- Password policy + pwned check (P1-026, T17): the policy is three rules in order — length >= 12 (asserted: 11 chars → 422 `too_short`), blocklist (asserted: `qwerty123456`, a single dictionary word at rank 1850, → 422 `common_password`; `qazxswedcvfr`, rank 10023 — just outside the top 10k — is NOT blocklisted but is still rejected as `too_weak`, pinning the cutoff; a longer password that merely contains a common word, `Sunshine-42-rain` (contains `sunshine`, rank 46), is not blocklisted and scores 3, so it is accepted), strength zxcvbn >= 3 (asserted: `123456789012` scores 1, `abcdefghijkl` scores 0, `Password1234` scores 1, `dragonballz99` scores 1 — all 422 `too_weak`; `correct horse battery staple` scores 4 and `pässwörd-1234` scores 4, both accepted; `letmein2024!!` scores exactly 3 and is accepted — the boundary is the crate's own pass line). The same rules gate the reset flow's new password (asserted: reset with `123456789012` → 422 `too_weak`, token not consumed). The HIBP k-anonymity check is off by default (asserted: `Settings::default().password_pwned_check` is false; registering `letmein2024!!` with default settings is 201 — no HIBP call is made) and, when on, rejects a breached password with 422 `pwned_password` (asserted end to end against a local stub server standing in for the range API: register with `letmein2024!!` → 422; the same password registers 201 when the stub's range does not contain its suffix; a stub outage — closed port — fails open and registration proceeds; the reset flow with a breached new password → 422 and the token survives for a clean retry — asserted: the same token then resets to a clean password with 204). The k-anonymity math is unit-tested (asserted: `password` SHA-1 splits to prefix `5BAA6` + suffix `1E4C9B93F3F0682250B6CF8331B7EE68FD8`; range parsing is case-insensitive and ignores malformed lines).
- Profile + auth extractor (P1-005): `GET`/`PATCH /v1/me` without a credential, with a malformed JWT, or with a valid JWT for an unknown user is 401 `PF-1001`; an expired JWT is 401 `PF-1011` (the extractor's own unit test proves the three no-DB rejections; the integration tests prove the happy path and the unknown-user case through the real router). An unknown or revoked API key, or one whose owner is not `active`, is 401 `PF-1001` (P1-034 — a live key authenticates; see the P1-034 bullet); a session cookie, alone, is 401 `PF-1001` (P1-016, FINAL). The profile never leaks the password hash (asserted on the GET body); the email-change intent is duplicate-checked (409 `PF-2011`) and the `profile.update` audit carries the pending email as sha256 only.
- Email change (P1-006, T18): setting a pending email mints an `email_change` token + queues the verification mail to the new address and the takeover alert to the old address (the alert carries no token and never names the new address — asserted on the outbox rows); confirming swaps the email atomically (consume + swap + audit in one tx) and verifies the new address; a registration token at confirm is 401 `PF-1010` (wrong purpose, not consumed — asserted: the token still verifies afterwards); an expired change token is 401 `PF-1011` (not consumed); a cleared intent deletes the change token (confirm then 401s); an address taken meanwhile is 409 `PF-2011` with the token surviving (tx rolled back) and the intent still pending; a resend-verification kills a live change token (one live token per user — the pending intent survives and is re-triggered by clearing + re-setting).
- Account deletion (P1-007, T19): `DELETE /v1/me` requests deletion (204, `status = 'deletion_pending'`, `deleted_at` set — the account is NOT deleted yet, GET still works and shows the grace); a second DELETE is a no-op (grace runs from the first request — asserted: no refreshed `deleted_at`, no second audit row, no second mail); a login during the grace cancels it (asserted: status active, `deleted_at` cleared, one `account.delete_cancelled` audit row, and a second login after the cancel audits nothing more); the purge (`detag-gc --purge-users`) hard-deletes past-grace accounts with the full cascade (asserted: sessions, jobs, uploads, job events, attestations, subscriptions, usage counters, idempotency keys and verification tokens all gone; audit rows survive with the actor id intact — migration 20261113062352 dropped the actor FK and made the job_events / attestations triggers UPDATE-only, because the old contract blocked every purge of a user with history; see `migration_purge_cascade_triggers.rs`).
- Admin suspend / restore (P1-008, T20): an admin suspends a user (200, status `suspended`, both live sessions revoked — asserted via `sessions::list_for_user`, every `revoked_at` set — and every queued job held, `queued` → `held`; the `user.suspended` audit carries the reason + `{sessions_revoked, jobs_held}` in `after`); a non-admin gets 403 `PF-1002`, no credential gets 401 `PF-1001`, an unknown target gets 404 `PF-2010`, a missing or blank reason gets 422 `PF-2002` (asserted: the target is untouched by the rejection); suspending an already-suspended account is a 200 no-op (asserted: exactly one `user.suspended` audit); a restore returns the account to `active`, releases held jobs to `queued`, and leaves sessions revoked (asserted: the session row still has `revoked_at` — the user logs in again); restoring a non-suspended account is a 200 no-op (asserted: no `user.restored` audit); a suspend cancels a pending deletion (asserted: status `suspended`, `deleted_at` cleared); a suspended login is 403 `PF-1003` after a correct password and the generic 401 `PF-1001` after a wrong one (asserted: the suspended attempt audits `login.failure` with reason `suspended`); after a restore the login works again. The residual window is documented, not tested away: the access token already issued stays valid until it expires (≤ 15 min) — the extractor does not check status. Bonus finding (P1-008): the error mapper kept the framework's 400 wire status while the problem body said 422 — a malformed-UUID path param answered 400 with a 422 body; the mapper now stamps the wire status from the problem (its own docs already promised "a framework 400 becomes a 422 problem"), proven by the malformed-UUID test (422 `PF-2002`); the 404/413/415 mappings are unaffected (their problems carry the same status the framework sent).
- Admin user search (P1-009): `GET /v1/admin/users` lists users in `created_at` order (oldest first) with cursor pagination — five users, `limit=2`, walk all three pages in order with no duplicates and no skipped rows (asserted: the union of the pages is exactly the five, and the third page has no `next_cursor`); `?query=` filters by email prefix, display-name prefix (asserted: a query matching only the display name narrows to that user), and id prefix (asserted: every returned id carries the prefix); a query with no match is 200 with `items: []` and no cursor; `limit=0` clamps to 1 (asserted: one item + a cursor); a tampered cursor is 422 `PF-2002`; a non-numeric `limit` is 422 `PF-2002` (the `Query` extractor's rejection, rewritten by the error mapper); support may search (200 — read-only role), a plain user gets 403 `PF-1002`, no credential gets 401 `PF-1001`; a user with a live Pro subscription + today's usage row shows `plan: "pro"`, `images_used_today: 3`, `video_seconds_used_today: 120` (asserted), while users without either show `plan: "free"` and zeros. Test-isolation lesson: the harness DB persists across runs, so a test prefix must be unique per RUN — the first 8 hex chars of a UUID recur every ~65 s (they are the top of the unix-ms timestamp), and the previous run's users leaked into this run's filtered search until the prefix carried a full UUID (the email then carries no second UUID, or the local part exceeds the validator's 64-character cap — that was the earlier 422).
- Impersonation (P1-010, T21): an admin impersonates a user (200, `token_type: "Bearer"`, `expires_in: 900`, `impersonator_id` = the admin, `user_id` = the target; the token's claims are verified directly — `sub` + `role` are the target's, `impersonator_id` is the admin, `exp - iat` is exactly 900); the token acts as the target (`GET /v1/me` returns the target's profile, asserted); the token cannot reach admin endpoints (asserted: suspend is 403 `PF-1002`, the admin user list is 403 `PF-1002` — reads included); support gets 403 `PF-1002` (impersonation is a write), a plain user gets 403 `PF-1002`, no credential gets 401 `PF-1001`, an unknown target gets 404 `PF-2010`, a missing or blank reason gets 422 `PF-2002` (asserted: no `user.impersonated` audit for the rejections); the impersonation is audited once (`user.impersonated`, actor = the admin, target = the user, the reason verbatim, `after.expires_in` = 900); an expired impersonation token is 401 `PF-1011` (asserted with a token minted 60 s in the past — auto-expiry is the JWT `exp`, leeway 0; the service only ever issues 15-minute tokens). The banner contract is documented in the api-spec (the console MUST show both ids for the whole session); the per-action dual-id audit convention is P1-011's scope.
- Impersonation audit tests (P1-011, T21): every impersonated action's audit row carries BOTH ids — an impersonated profile update audits `profile.update` with `actor_user_id` = the admin and `target_id` = the user (asserted, incl. `after.display_name` = the new name, and `GET /v1/me` under the token shows it — the action worked as the user), and an impersonated deletion request audits `account.delete_requested` the same way (asserted; the account is `deletion_pending` afterwards); a normal (non-impersonated) profile update still audits actor == target == the user (regression asserted). The `user.impersonated` row itself is checked field by field (action, actor, `target_type: "user"`, target, `before` is None, `after.expires_in` = 900, reason verbatim). The admin block is proven on every live admin route (restore + impersonate + the user list, on top of P1-010's suspend — all 403 `PF-1002`; the stub admin routes carry no guard yet, their tickets add one with the real handler). An expired impersonation token cannot reach admin endpoints either — it is 401 `PF-1011`, not 403 (expiry is checked before the guards run, asserted on suspend + the user list). Impersonating an admin target is still blocked (asserted: the token's role is `admin`, but the block is on the impersonator marker, not the role — the user list is 403 while `GET /v1/me` works as the target admin). The code change this ticket needed: the audit actor is threaded through the profile + deletion services (`AuthContext::audit_actor_id` — the impersonator when impersonating, else the user; the handlers pass it explicitly, and the `ref user` borrow keeps `auth` usable after the unwrap).

## API & webhook hardening

- Body caps per route class (P0-104): auth/meta 64 KiB, jobs/admin 1 MiB, billing (webhooks) 256 KiB; over-cap is 413 PF-2003, tested per class. Uploads are exempt (bytes never transit the api).
- Dimension caps (P0-104, FR-U-04): 8000x8000 per side, 64 MP total, enforced at job-create by `validate_dimensions` (PF-2005, 413, fail-closed on missing dimensions); the sniff-time dimension check in the abuse table above lands with intake (Phase 2/3).
- Webhook SSRF: endpoint URL must resolve to public HTTPS; private/link-local CIDRs denied; redirect-following disabled; tested with a listener on 169.254.169.254-style address.
- Outbound webhook HMAC: constant-time compare; replay window enforced; tampered payload rejected.
- Idempotency: replayed Idempotency-Key returns original response; concurrent duplicates create one job (integration test with racing requests).
- Rate limits: per-IP + per-route token buckets enforced by the middleware (P0-103; race-safe — no over-admission under concurrency, proven by test); service buckets per-account login (P1-003) + per-IP login (P1-020) + per-email register (P1-020) + per-account reset (P1-020, wired by P1-025), each with its own key segment (one bucket, one key) and proven race-safe (50 concurrent spends admit exactly the burst per bucket, P1-020); a service denial's 429 carries the denying bucket's trio — the middleware never overwrites it (P1-020); lockout backoff curve asserted.
- Injection: sqlx parameterized everywhere (CI grep forbids `format!`-built SQL); no string-built shell calls (ffmpeg args as argv array, never shell string).

## Headers & transport

CSP (web), HSTS (prod only — dev is plain http, so dev responses carry the rest of the table but no HSTS), X-Content-Type-Options, Referrer-Policy, frame-ancestors none for app routes; the Swagger UI at `/docs` gets its own same-origin CSP (the api's `default-src 'none'` would block its JS) — asserted by a route test against a header table. TLS terminated at caddy in prod; internal services never exposed (compose networks: `internal` vs `edge`).
